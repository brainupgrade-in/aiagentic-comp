01

Docker Fundamentals

Why containers matter for AI deployment

Why Docker for AI?

The Problem

  • "Works on my machine" — Python version, pip packages, OS libs
  • AI apps have complex dependencies (PyTorch, LangChain, ChromaDB)
  • Different environments: dev, staging, production
  • Team members need identical setups

The Docker Solution

  • Package everything — code, runtime, libraries, config
  • Run anywhere — laptop, server, cloud, Kubernetes
  • Reproducible — same image = same behavior
  • Isolated — no conflicts between applications
A Docker container is like a shipping container for software. Just as shipping containers standardized global trade (any port, any ship), Docker containers standardize software delivery (any server, any cloud).

Images, Containers & Layers

Image (Blueprint)

  • Read-only template
  • Built from a Dockerfile
  • Composed of layers (stacked filesystem changes)
  • Shareable via registries

Container (Instance)

  • Running instance of an image
  • Adds a thin writable layer on top
  • Isolated process with its own filesystem
  • Ephemeral by default (data lost on remove)

Docker Fundamentals Summary

1. Docker solves "works on my machine" by packaging everything together

2. Containers share the host kernel — faster and lighter than VMs

3. Images are read-only blueprints; containers are running instances

4. Images are built from layers — each Dockerfile instruction creates a layer

5. Registries (Docker Hub, ECR) store and distribute images

Dockerfile for LangChain

Containerizing your AI agent application

Core Dockerfile Instructions

Instruction Purpose Example
FROM Base image to build on FROM python:3.11-slim
WORKDIR Set working directory WORKDIR /app
COPY Copy files from host to image COPY . /app
RUN Execute command during build RUN pip install -r requirements.txt
ENV Set environment variables ENV PYTHONUNBUFFERED=1
EXPOSE Document listening port EXPOSE 8000
CMD Default command to run CMD ["uvicorn", "main:app"]

Basic LangChain Dockerfile

Dockerfile
# Base image with Python 3.11 FROM python:3.11-slim # Set working directory WORKDIR /app # Copy requirements first (for layer caching) COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt # Copy application code COPY . . # Environment variables ENV PYTHONUNBUFFERED=1 # Expose the FastAPI port EXPOSE 8000 # Start the application CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Layer Caching — The #1 Optimization

Docker caches each layer. If a layer hasn't changed, it's reused instantly.

Bad: Cache busted every time

# COPY everything first COPY . . # any code change busts this RUN pip install -r req.txt # reinstalls every time!

Every code change → reinstall all packages (~2-5 min)

Good: Dependencies cached

# Copy ONLY requirements first COPY requirements.txt . # rarely changes RUN pip install -r req.txt # cached if req unchanged COPY . . # code changes don't bust deps

Code change → only re-copy code (~seconds)

Rule: Put things that change less frequently earlier in the Dockerfile. Dependencies change rarely; code changes often.

Multi-Stage Builds

Build in one stage, run in another — smaller final image

# Stage 1: Build (install everything, compile deps) FROM python:3.11-slim AS builder WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir --prefix=/install -r requirements.txt # Stage 2: Run (only copy what's needed) FROM python:3.11-slim WORKDIR /app # Copy only installed packages from builder COPY --from=builder /install /usr/local COPY . . ENV PYTHONUNBUFFERED=1 EXPOSE 8000 CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Why Multi-Stage?

Build tools, compilers, and temp files stay in stage 1. Final image only contains runtime essentials.

Size Savings

Single stage: ~1.2 GB. Multi-stage: ~400 MB. Less to push, pull, and store.

Use python:3.11-slim for AI apps. It has enough for pip to work but skips compilers and docs. Avoid alpine for ML — many C extensions won't compile.

Dockerfile Summary

1. Use python:3.11-slim as base — small but compatible

2. Copy requirements.txt first, then install, then copy code — layer caching

3. Use --no-cache-dir with pip to avoid storing download cache in the image

4. Multi-stage builds keep the final image small (build tools stay in stage 1)

5. Set PYTHONUNBUFFERED=1 so logs appear immediately in docker logs

03

AI-Specific Patterns

Docker patterns tailored for LangChain and LLM applications

Managing Large Dependencies

AI packages are big — LangChain + ChromaDB + models can exceed 2 GB

# Split requirements for better caching # requirements-base.txt: rarely changes (langchain, fastapi, chromadb) # requirements-dev.txt: changes more often (your custom packages) COPY requirements-base.txt . RUN pip install --no-cache-dir -r requirements-base.txt COPY requirements-dev.txt . RUN pip install --no-cache-dir -r requirements-dev.txt COPY . .

Why Split?

langchain and chromadb rarely change version. Putting them in a separate layer means they're cached even when you add a new small package.

.dockerignore

Exclude .git/, __pycache__/, .env, *.pyc, .venv/ from the build context. Smaller context = faster builds.

The .dockerignore File

Exclude files from the build context — like .gitignore for Docker

# .dockerignore .git .gitignore __pycache__ *.pyc .env .env.* .venv/ venv/ *.egg-info .pytest_cache .mypy_cache tests/ docs/ README.md Dockerfile docker-compose.yml

Without .dockerignore

Sends entire directory (including .git, .venv, data files) to Docker daemon. Build context: 500+ MB.

With .dockerignore

Only sends source code and config. Build context: ~5 MB. Much faster builds.

Non-Root User for Security

Never run containers as root in production

FROM python:3.11-slim WORKDIR /app # Install dependencies as root COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt # Create non-root user RUN useradd --create-home --shell /bin/bash appuser # Copy code and set ownership COPY --chown=appuser:appuser . . # Switch to non-root user USER appuser EXPOSE 8000 CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
If a container is compromised, a non-root user limits the blast radius. The attacker can't install packages, modify system files, or escape to the host.

Health Checks

Let Docker (and Kubernetes) know if your app is healthy

# In Dockerfile: tell Docker how to check health HEALTHCHECK --interval=30s --timeout=5s --retries=3 \ CMD curl -f http://localhost:8000/health || exit 1
# In FastAPI: the health endpoint @app.get("/health") async def health(): return { "status": "healthy", "agent": "ready", "version": "2.0.0", }

interval

How often to check (30s default)

timeout

Max time for check to respond

retries

Failures before "unhealthy"

Model & Embedding Caching

Avoid re-downloading models every time the container starts

# Option 1: Bake models into the image (larger but self-contained) RUN python -c "from sentence_transformers import SentenceTransformer; \ SentenceTransformer('all-MiniLM-L6-v2')" # Option 2: Mount a volume (smaller image, shared cache) # docker run -v model-cache:/root/.cache myapp:1.0 # Option 3: Use environment variable for cache directory ENV TRANSFORMERS_CACHE=/app/models ENV SENTENCE_TRANSFORMERS_HOME=/app/models

Bake into Image

Image is larger (~1+ GB) but fully self-contained. No network needed at startup. Best for air-gapped deployments.

Docker Volume

Mount a persistent volume for model cache. First run downloads; subsequent runs are instant. Best for Kubernetes.

Production Dockerfile — Complete

Dockerfile
FROM python:3.11-slim AS builder WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir --prefix=/install -r requirements.txt FROM python:3.11-slim WORKDIR /app # Install curl for health checks RUN apt-get update && apt-get install -y --no-install-recommends curl \ && rm -rf /var/lib/apt/lists/* # Copy installed packages from builder COPY --from=builder /install /usr/local # Create non-root user RUN useradd --create-home appuser # Copy application code COPY --chown=appuser:appuser . . ENV PYTHONUNBUFFERED=1 USER appuser EXPOSE 8000 HEALTHCHECK --interval=30s --timeout=5s --retries=3 \ CMD curl -f http://localhost:8000/health || exit 1 CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

When to Scan

After every build, in CI/CD pipeline, and periodically for running images.

How to Fix

Update base image, upgrade packages, or switch to a patched version.

AI Docker Patterns Checklist

1. Split requirements into base (large, stable) and dev (small, changing)

2. Add .dockerignore to exclude .git, .env, __pycache__, venv

3. Run as non-root user — create with useradd, switch with USER

4. Add HEALTHCHECK pointing to your /health endpoint

5. Cache models via Docker volumes or bake into the image

6. Scan with Trivy before deploying to production

What is the key difference between containers and virtual machines?
A Containers include a full guest operating system
B Containers share the host kernel, making them lighter and faster to start
C VMs are faster than containers because they have dedicated hardware
D There is no difference — they are the same technology
Why B? Containers share the host OS kernel and only package the application and its dependencies. This means they start in seconds (vs minutes for VMs), use MBs of disk (vs GBs), and you can run 100+ per host (vs ~10 VMs).

C They are the same thing — different names for the same concept

Why should you COPY requirements.txt and RUN pip install before COPY . .?
A To make the Dockerfile easier to read
B Because Docker requires this exact order or it will fail
C So Docker can cache the dependency layer — code changes don't trigger a full reinstall
D To prevent security vulnerabilities in the final image
Why C? Docker caches each layer. If requirements.txt hasn't changed, the pip install layer is reused from cache instantly. Without this ordering, any code change invalidates the dependency layer, forcing a full reinstall (~2-5 minutes) on every build.

What is the purpose of a multi-stage Docker build?
A To run multiple applications in a single container
B To keep build tools in one stage and copy only runtime artifacts to the final image, reducing size
C To create different images for different operating systems
D To run tests automatically during the build process
Why B? Multi-stage builds use separate FROM instructions. The first stage installs build tools, compilers, and dependencies. The second stage starts fresh and copies only the compiled output. Result: ~400 MB instead of ~1.2 GB for AI applications.

Why should production Docker containers run as a non-root user?
A Non-root users make the container start faster
B Docker requires non-root users for all containers
C To limit damage if the container is compromised — attacker can't modify system files or escape
D To reduce the size of the Docker image
Why C? This is the principle of least privilege. If an attacker exploits a vulnerability in your AI agent, a non-root user prevents them from installing backdoors, reading sensitive system files, or potentially escaping the container to the host system.
