01

Kubernetes Overview

Why K8s matters for production AI workloads

Why Kubernetes for AI?

The Problem with Docker Alone

  • What if the container crashes at 3 AM?
  • How do you run 10 replicas across servers?
  • How do you deploy a new version without downtime?
  • How do you scale up when traffic spikes?

What Kubernetes Does

  • Self-healing — restarts crashed containers
  • Scaling — run N replicas, auto-scale on load
  • Rolling updates — zero-downtime deployments
  • Service discovery — containers find each other
Docker is a shipping container. Kubernetes is the container port — it decides where containers go, restarts broken ones, and routes traffic to healthy ones.

Docker Compose vs Kubernetes

Docker Compose Kubernetes
Best for Local dev, small deployments Production at scale
Self-healing restart: unless-stopped Full: restarts, reschedules, health checks
Scaling Manual (docker compose up --scale) Auto-scaling (HPA)
Updates Stop & restart (downtime) Rolling updates (zero downtime)
Multi-host Single machine only Cluster of machines
Config docker-compose.yml YAML manifests (more verbose, more powerful)
Docker Compose is great for development. Kubernetes is for production — when your AI agent needs to be always available, scalable, and self-healing.

K8s Overview Summary

1. Kubernetes orchestrates containers — self-healing, scaling, zero-downtime deploys

2. Control Plane (brain) decides; Worker Nodes (muscle) execute

3. Declarative model — you describe desired state, K8s makes it happen

4. kubectl is the CLI to interact with the cluster

5. For production AI: K8s handles restarts, scaling, updates automatically

Core Objects

Pods, Deployments, Services, ConfigMaps, Secrets

Pods — Smallest Deployable Unit

What is a Pod?

  • Wrapper around one or more containers
  • Shared network (localhost) and storage
  • Has its own IP address inside the cluster
  • Ephemeral — can be replaced at any time

Pod = Container + Context

Pod: agent-7f4d9
AI Agent
:8000
IP: 10.244.1.15
A Pod is like an apartment. Containers inside share the same address (IP), kitchen (storage), and phone line (network). Usually one container per pod, but sometimes a helper “sidecar” container lives alongside.

Pod Manifest (YAML)

pod.yaml
apiVersion: v1 kind: Pod metadata: name: unigps-agent labels: app: agent spec: containers: - name: agent image: unigps-agent:2.0 ports: - containerPort: 8000 resources: requests: memory: "256Mi" cpu: "250m" limits: memory: "512Mi" cpu: "500m"

apiVersion + kind

What type of resource to create (Pod, Deployment, Service...)

metadata

Name, labels, and annotations for identification and selection.

spec

The desired state: which containers, ports, resources, volumes.

Deployments — Declarative Updates

Don't create Pods directly. Use a Deployment to manage them.

What a Deployment Does

  • Manages a ReplicaSet of identical Pods
  • Self-healing: pod dies → new one created
  • Rolling updates: gradual version change
  • Rollback: undo a bad deployment
  • Scales up/down with one command

Deployment → ReplicaSet → Pods

Services — Network Abstraction

Pods are ephemeral. A Service gives them a stable address.

Problem: Pods Come and Go

  • Each pod gets a unique IP
  • When a pod dies & restarts, it gets a new IP
  • You can't hardcode pod IPs

Solution: Service

  • Stable DNS name (e.g., agent-svc)
  • Load balances across all matching pods
  • Pods come/go; service address stays

ConfigMaps & Secrets

Separate configuration from container images

ConfigMap (non-sensitive)

apiVersion: v1 kind: ConfigMap metadata: name: agent-config data: LOG_LEVEL: "info" APP_VERSION: "2.0.0" REDIS_URL: "redis://redis:6379"

Secret (sensitive, base64)

apiVersion: v1 kind: Secret metadata: name: agent-secrets type: Opaque data: GROQ_API_KEY: Z3NrX2FiYzEyMw==
ConfigMaps for non-sensitive settings (log levels, URLs). Secrets for API keys and passwords (base64-encoded, not encrypted by default — use external secret managers in production).

Using Config in Pods

deployment.yaml (excerpt)
spec: containers: - name: agent image: unigps-agent:2.0 envFrom: # Inject ALL keys as env vars - configMapRef: name: agent-config # LOG_LEVEL, APP_VERSION, REDIS_URL - secretRef: name: agent-secrets # GROQ_API_KEY env: # Or inject individual keys - name: PYTHONUNBUFFERED value: "1"

envFrom

Injects all keys from a ConfigMap or Secret as environment variables. Clean and simple.

env with valueFrom

Pick individual keys. Useful when you need to rename vars or combine sources.

Core Objects Summary

1. Pod — smallest unit; wraps one or more containers with shared network/storage

2. Deployment — manages pod replicas, rolling updates, self-healing

3. Service — stable DNS/IP for pods; ClusterIP (internal), NodePort, LoadBalancer

4. ConfigMap — non-sensitive config injected as environment variables

5. Secret — sensitive data (API keys); base64-encoded, injected the same way

AI Workload Considerations

Running LangChain agents reliably on Kubernetes

Resource Requests & Limits

AI workloads are resource-hungry. Tell K8s what you need.

resources: requests: # Minimum guaranteed resources memory: "512Mi" # Scheduler uses this to place pod cpu: "250m" # 250 millicores = 0.25 CPU limits: # Maximum allowed resources memory: "1Gi" # OOMKilled if exceeded cpu: "1000m" # Throttled if exceeded

requests (Minimum)

  • Guaranteed to the pod
  • Scheduler uses this to place pods on nodes
  • Set to what your app normally uses

limits (Maximum)

  • Pod cannot exceed this
  • Memory exceeded → OOMKilled
  • CPU exceeded → throttled (not killed)

Resource Guidelines for AI Apps

Component Memory Request Memory Limit CPU Request
FastAPI + LangChain Agent 256–512 Mi 1 Gi 250m
ChromaDB (vector store) 512 Mi–1 Gi 2 Gi 500m
Redis (cache) 64–128 Mi 256 Mi 100m
Embedding model (local) 1–4 Gi 4–8 Gi 1000m+
Start small, monitor, then adjust. Under-requesting wastes node resources. Under-limiting risks OOMKills. Check kubectl top pods for actual usage.

Readiness & Liveness Probes

K8s needs to know: Is your agent ready? Is it alive?

Liveness Probe

  • "Is the container alive?"
  • Fails → K8s restarts the container
  • Catches: deadlocks, infinite loops

Readiness Probe

  • "Is the container ready for traffic?"
  • Fails → K8s stops sending traffic
  • Catches: model loading, warmup time
livenessProbe: httpGet: path: /health port: 8000 initialDelaySeconds: 10 # Wait 10s before first check periodSeconds: 15 # Check every 15s readinessProbe: httpGet: path: /health port: 8000 initialDelaySeconds: 5 periodSeconds: 10

Why Probes Matter for AI Agents

Scenario: Model Loading

Your AI agent takes 30 seconds to load embeddings at startup.

  • Without readiness probe: K8s sends traffic immediately → 500 errors
  • With readiness probe: K8s waits until /health returns 200 → smooth start

Scenario: LLM Timeout

Your agent's LLM call hangs — the process is stuck.

  • Without liveness probe: Pod looks "running" but is dead → silent failure
  • With liveness probe: /health times out → K8s restarts the pod automatically
The /health endpoint from Session 9 (FastAPI) is exactly what K8s probes need. Same endpoint, different consumer — Docker HEALTHCHECK in Session 10, Kubernetes probes here.

Complete AI Agent Deployment

deployment.yaml (production)
apiVersion: apps/v1 kind: Deployment metadata: name: unigps-agent spec: replicas: 3 selector: matchLabels: app: agent template: metadata: labels: app: agent spec: containers: - name: agent image: unigps-agent:2.0 ports: - containerPort: 8000 envFrom: - configMapRef: name: agent-config - secretRef: name: agent-secrets resources: requests: { memory: "256Mi", cpu: "250m" } limits: { memory: "1Gi", cpu: "1000m" } livenessProbe: httpGet: { path: /health, port: 8000 } initialDelaySeconds: 10 periodSeconds: 15 readinessProbe: httpGet: { path: /health, port: 8000 } initialDelaySeconds: 5 periodSeconds: 10

AI Workloads Checklist

1. Set resource requests to what your app normally uses

2. Set resource limits to the maximum you'll tolerate

3. Add readiness probe — critical for agents with model loading time

4. Add liveness probe — catches stuck processes and LLM timeouts

5. Use ConfigMaps for settings, Secrets for API keys

6. Monitor with kubectl top pods and adjust resources based on actual usage

Answer: Question 1
What is the primary advantage of Kubernetes over Docker Compose for production?
A Kubernetes uses YAML files while Docker Compose uses JSON
B Kubernetes provides self-healing, auto-scaling, and zero-downtime updates across a cluster
C Kubernetes builds Docker images faster than Docker Compose
D Kubernetes doesn't need Docker images to run containers
Why B? Docker Compose runs on a single machine with basic restart policies. Kubernetes runs across a cluster, automatically restarts failed pods, scales replicas based on load (HPA), and performs rolling updates with zero downtime.

Answer: Question 2
In Kubernetes architecture, what does the Control Plane do?
A It runs application containers directly
B It builds Docker images for the cluster
C It makes scheduling decisions, stores cluster state, and maintains desired state
D It serves as a load balancer for external traffic
Why C? The Control Plane is the "brain" of Kubernetes. The API Server accepts requests, etcd stores cluster state, the Scheduler places pods on nodes, and the Controller Manager continuously reconciles desired state with actual state. Worker Nodes run the actual containers.

Answer: Question 3
Why should you use a Deployment instead of creating Pods directly?
A Pods cannot run containers — only Deployments can
B Deployments manage replicas, self-healing, rolling updates, and rollbacks
C Deployments are faster to create than Pods
D Pods don't support environment variables
Why B? A bare Pod that crashes stays dead. A Deployment watches over its pods — if one dies, it creates a replacement. It also handles rolling updates (gradually replacing old pods with new ones) and rollbacks (reverting if something goes wrong). Always use Deployments for production workloads.

B Services encrypt all network traffic between pods

Answer: Question 5
Why is a readiness probe especially important for AI agent pods?
A It makes the pod start faster by skipping container initialization
B It prevents traffic from reaching pods that are still loading models or warming up
C It automatically downloads the latest model version
D It reduces memory usage during startup
Why B? AI agents often need 30+ seconds to load models or warm up caches. Without a readiness probe, K8s routes traffic to the pod immediately — causing 500 errors. The readiness probe checks /health and only adds the pod to the Service endpoint pool once it returns 200. This is the same /health endpoint from Sessions 9 and 10.
