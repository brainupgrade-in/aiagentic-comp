Prometheus Architecture

Pull-Based Metrics Collection

Pull vs Push Metrics

Pull-Based (Prometheus)

  • Prometheus scrapes targets on a schedule
  • Targets expose metrics at /metrics endpoint
  • If a target goes down, Prometheus detects it (no data = problem)
  • Simpler for apps — just expose an HTTP endpoint
# Prometheus pulls every 15s Prometheus → GET /metrics → agent-api Prometheus → GET /metrics → redis Prometheus → GET /metrics → chromadb

Push-Based (e.g., StatsD)

  • Apps push metrics to a collector
  • Requires apps to know the collector address
  • If app crashes mid-push, data may be lost
  • Useful for short-lived jobs (batch, cron)
# Apps push metrics agent-api → PUSH metrics → Collector redis → PUSH metrics → Collector chromadb → PUSH metrics → Collector
Pull = a doctor checking your vitals on scheduled visits. Push = you calling the doctor every time your heart beats. Pull is more practical for monitoring many patients.

Prometheus Configuration

# prometheus.yml global: scrape_interval: 15s # How often to scrape targets evaluation_interval: 15s # How often to evaluate alert rules scrape_configs: # Our AI agent API - job_name: "agent-api" metrics_path: /metrics static_configs: - targets: ["agent-api:8000"] labels: environment: "production" # Redis (via redis-exporter sidecar) - job_name: "redis" static_configs: - targets: ["redis-exporter:9121"] # Kubernetes service discovery (auto-find pods) - job_name: "kubernetes-pods" kubernetes_sd_configs: - role: pod relabel_configs: - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape] action: keep regex: "true"

K8s Service Discovery

Prometheus auto-discovers pods with the right annotations

# Add these annotations to your Pod template apiVersion: apps/v1 kind: Deployment metadata: name: agent-api spec: template: metadata: annotations: prometheus.io/scrape: "true" # Tell Prometheus to scrape this pod prometheus.io/port: "8000" # Which port to scrape prometheus.io/path: "/metrics" # Which path (default: /metrics) spec: containers: - name: agent image: agent-api:2.0 ports: - containerPort: 8000
With K8s service discovery, Prometheus automatically finds new pods as they scale up. No manual config changes needed when you add replicas.

PromQL — Query Language

Prometheus Query Language for querying time-series data

Query What It Returns
agent_requests_total Current counter value for all label combinations
agent_requests_total{endpoint="/chat"} Filtered by endpoint label
rate(agent_requests_total[5m]) Requests per second (averaged over 5 minutes)
sum(rate(agent_requests_total[5m])) Total RPS across all endpoints and instances
histogram_quantile(0.99, rate(agent_request_duration_seconds_bucket[5m])) p99 latency in seconds
Never use a raw counter value directly (e.g., agent_requests_total) in dashboards. Counters only go up. Use rate() or increase() to get meaningful per-second or per-interval values.

Essential PromQL Functions

Function Use Case Example
rate() Per-second rate of a counter rate(http_requests_total[5m])
increase() Total increase in time window increase(tokens_total[1h])
sum() Aggregate across labels sum by (model)(rate(...))
avg() Average across instances avg(agent_active_connections)
histogram_quantile() Percentile from histogram histogram_quantile(0.95, ...)
absent() Detect missing metric (target down) absent(up{job="agent-api"})
# Real-world PromQL: Error rate as percentage sum(rate(agent_requests_total{status=~"5.."}[5m])) / sum(rate(agent_requests_total[5m])) * 100

Alert Rules

# alerting-rules.yml groups: - name: agent-alerts rules: # High error rate - alert: HighErrorRate expr: | sum(rate(agent_requests_total{status=~"5.."}[5m])) / sum(rate(agent_requests_total[5m])) > 0.05 for: 5m labels: severity: critical annotations: summary: "Error rate above 5% for 5 minutes" # High latency - alert: HighLatency expr: | histogram_quantile(0.99, rate(agent_request_duration_seconds_bucket[5m])) > 5 for: 10m labels: severity: warning annotations: summary: "p99 latency above 5 seconds" # Target down - alert: AgentDown expr: up{job="agent-api"} == 0 for: 1m labels: severity: critical

AI Metrics Categories

Request Metrics

  • COUNTER Total requests by endpoint
  • HISTOGRAM Request latency (p50, p90, p99)
  • COUNTER Errors by type (4xx, 5xx)
  • GAUGE Active concurrent requests

LLM Metrics

  • COUNTER Tokens consumed (in/out)
  • HISTOGRAM LLM call duration
  • COUNTER LLM calls by model
  • COUNTER Estimated cost (USD)

RAG Metrics

  • HISTOGRAM Retrieval latency
  • HISTOGRAM Documents retrieved per query
  • COUNTER Cache hits vs misses
  • GAUGE Collection size (vectors)

Infrastructure Metrics

  • GAUGE CPU/memory utilization
  • GAUGE GPU utilization (if applicable)
  • GAUGE Queue depth
  • HISTOGRAM Processing time per task

Exposing Metrics in FastAPI

from prometheus_client import ( Counter, Histogram, Gauge, generate_latest, CONTENT_TYPE_LATEST ) from fastapi import FastAPI, Response import time app = FastAPI() # Define metrics REQUEST_COUNT = Counter( "agent_requests_total", "Total agent requests", ["endpoint", "status"] ) REQUEST_LATENCY = Histogram( "agent_request_duration_seconds", "Request duration in seconds", ["endpoint"], buckets=[0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0] ) TOKENS_TOTAL = Counter( "agent_tokens_total", "Total tokens consumed", ["model", "direction"] # direction: input/output ) ACTIVE_REQUESTS = Gauge( "agent_active_requests", "Currently processing requests" ) # Expose /metrics endpoint for Prometheus @app.get("/metrics") def metrics(): return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

Recording Metrics in Handlers

@app.post("/chat") async def chat(query: str): ACTIVE_REQUESTS.inc() # Gauge up start = time.time() try: # Call the AI agent result = await agent.process(query) # Record LLM token usage TOKENS_TOTAL.labels( model="llama3-70b", direction="input" ).inc(result.prompt_tokens) TOKENS_TOTAL.labels( model="llama3-70b", direction="output" ).inc(result.completion_tokens) REQUEST_COUNT.labels( endpoint="/chat", status="200" ).inc() return {"response": result.content} except Exception as e: REQUEST_COUNT.labels( endpoint="/chat", status="500" ).inc() raise finally: duration = time.time() - start REQUEST_LATENCY.labels(endpoint="/chat").observe(duration) ACTIVE_REQUESTS.dec() # Gauge down

Token & Cost Tracking

Track spending per model, endpoint, and time period

# Cost estimation metric ESTIMATED_COST = Counter( "agent_estimated_cost_usd", "Estimated cost in USD", ["model"] ) # Pricing table (per 1M tokens) PRICING = { "llama3-70b": {"input": 0.59, "output": 0.79}, "llama3-8b": {"input": 0.05, "output": 0.08}, "mixtral-8x7b": {"input": 0.24, "output": 0.24}, } def record_cost(model, prompt_tokens, completion_tokens): prices = PRICING.get(model, {"input": 0, "output": 0}) cost = (prompt_tokens * prices["input"] + completion_tokens * prices["output"]) / 1_000_000 ESTIMATED_COST.labels(model=model).inc(cost)
# PromQL: Daily cost by model sum by (model) (increase(agent_estimated_cost_usd[24h])) # PromQL: Cost per request (average over 1 hour) sum(rate(agent_estimated_cost_usd[1h])) / sum(rate(agent_requests_total{endpoint="/chat"}[1h]))

Dashboard Design Principles

The RED Method

For request-driven services:

  • Rate — requests per second
  • Errors — error rate (%)
  • Duration — latency distribution (p50, p90, p99)

The USE Method

For infrastructure resources:

  • Utilization — % of resource used
  • Saturation — queue length, waiting work
  • Errors — resource error counts

Layout Best Practices

  • Top row: stat panels (single big numbers)
  • Middle: time-series graphs (trends)
  • Bottom: tables (detailed breakdown)
  • Left to right: overview → detail

Common Mistakes

  • Too many panels — focus on 8–12 per dashboard
  • Using raw counter values (always use rate())
  • No alert thresholds visible on graphs
  • Missing time range controls

Grafana Alerts

Grafana can also evaluate alert rules (in addition to Prometheus Alertmanager)

Grafana Alert Rules

  • Defined visually in the dashboard UI
  • Multi-step conditions (AND/OR)
  • Supports any data source (not just Prometheus)
  • Contact points: Slack, email, PagerDuty, webhooks

AI-Specific Alert Examples

  • Token burn rate > 2x normal for 10 min
  • LLM latency p99 > 10s for 5 min
  • Cost rate > $5/hour for 30 min
  • ChromaDB retrieval returning 0 docs
  • Agent error rate > 5% for 5 min
Combine Prometheus Alertmanager for infrastructure alerts with Grafana Alerts for complex multi-source conditions (e.g., high cost AND high error rate).

Question 1 of 5

How does Prometheus collect metrics from your application?

A Your app pushes metrics to Prometheus every second
B Prometheus pulls (scrapes) your app’s /metrics endpoint on a schedule
C Prometheus reads metrics from log files on disk
D Metrics are collected via the Kubernetes API server
B — Pull-based scraping. Prometheus actively scrapes each target’s /metrics endpoint at the configured scrape_interval (default 15s). This is a core architectural choice that makes target health detection automatic.
Question 2 of 5

What PromQL function should you use to get “requests per second” from a counter?

A sum(agent_requests_total)
B rate(agent_requests_total[5m])
C avg(agent_requests_total)
D histogram_quantile(0.99, agent_requests_total)
B — rate(). rate() calculates the per-second average rate of increase of a counter over the given time window. Never display raw counter values — they only go up and aren’t meaningful on their own.
Question 3 of 5

Which Prometheus metric type should you use for tracking LLM call duration?

A Counter — count total duration
B Gauge — track current duration
C Histogram — observe duration distribution (p50, p90, p99)
D Summary — it’s only for durations
C — Histogram. Histograms bucket observations into predefined ranges, allowing you to calculate percentiles (p50, p90, p99) using histogram_quantile(). Essential for understanding latency distributions where averages hide outliers.
Question 4 of 5

What does the RED method stand for in dashboard design?

A Resources, Errors, Deployment
B Requests, Events, Duration
C Rate, Errors, Duration
D Reliability, Efficiency, Durability
C — Rate, Errors, Duration. The RED method focuses on request-driven services: how many requests/s (Rate), what percentage fail (Errors), and how long they take (Duration). It complements the USE method for infrastructure resources.
Question 5 of 5

How do you make Prometheus auto-discover pods on Kubernetes?

A Add each pod IP manually to prometheus.yml
B Install a Prometheus sidecar in every pod
C Use kubernetes_sd_configs with pod annotations (prometheus.io/scrape: "true")
D Prometheus automatically discovers all pods without configuration
C — K8s service discovery with annotations. Prometheus uses kubernetes_sd_configs to query the K8s API for pods, then relabel_configs to filter for pods with prometheus.io/scrape: "true". This auto-detects new pods as they scale.
