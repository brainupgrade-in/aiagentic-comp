Why RAG?

The Problem · The Architecture · Embedding Models

The Problem with LLMs Alone

LLMs know a lot, but not your data

What LLMs Can't Do

  • Answer questions about your company's docs
  • Know what happened after their training cutoff
  • Access your private PDFs, wikis, or databases
  • Reference specific page numbers or sources

They hallucinate when they don't know

What RAG Enables

  • Query your own documents with natural language
  • Get answers grounded in real sources
  • Always up-to-date — just add new docs
  • Include citations: "According to page 5..."

Grounded answers, not guesses

What is RAG?

Retrieval-Augmented Generation is a pattern where the LLM first retrieves relevant information from your data, then generates a response grounded in that information — instead of relying solely on its training data.

Retrieve

Find the most relevant chunks from your documents

Augment

Inject those chunks into the LLM's prompt as context

Generate

LLM generates an answer using the provided context

An open-book exam. The student (LLM) is smart, but instead of guessing answers from memory, they first look up relevant pages in the textbook (your documents), then write their answer based on what they found. The answer is grounded in real material.

Embedding Models

Turning text into numbers that capture meaning

An embedding is a list of numbers (a vector) that represents the meaning of a piece of text. Similar texts produce similar vectors.

Example

"king" → [0.21, -0.45, 0.87, ...]
"queen" → [0.19, -0.42, 0.85, ...]
"bicycle" → [-0.76, 0.33, -0.12, ...]

King and queen are close in vector space. Bicycle is far away.

Why This Matters for RAG

When you ask "What is the return policy?", the embedding of your question is compared to embeddings of all document chunks. The closest matches are the most relevant.

GPS coordinates for meaning. Just as GPS coordinates let you find nearby restaurants, embeddings let you find documents with similar meaning — even if they use different words. "refund policy" is close to "return procedure" in embedding space.

Embeddings in LangChain

from langchain_community.embeddings import HuggingFaceEmbeddings

# Initialize the embedding model (runs locally, no API key needed)
embeddings = HuggingFaceEmbeddings(
    model_name="all-MiniLM-L6-v2"
)

# Embed a single text
vector = embeddings.embed_query("What is the refund policy?")
print(len(vector))  # 384 dimensions

# Embed multiple documents
docs = ["Refund within 30 days", "Free shipping over Rs 500"]
vectors = embeddings.embed_documents(docs)
print(len(vectors))  # 2 vectors, each 384 dimensions
all-MiniLM-L6-v2 is a small, fast model (80 MB) that runs locally with no API key. It produces 384-dimensional vectors — good enough for most RAG applications.

Max Marginal Relevance Balances relevance with diversity of results Avoiding redundant results

Vector Stores & ChromaDB

Architecture · Collections · Metadata · Search

What is a Vector Store?

A database designed for similarity search

Regular Database (SQL)

  • Stores rows and columns
  • Exact match: WHERE name = 'Raj'
  • Can't search by meaning

"Find rows where city = Mumbai"

Vector Database (ChromaDB)

  • Stores vectors (embeddings) + text + metadata
  • Similarity search: "find similar meaning"
  • Returns ranked results by relevance

"Find docs about Indian cities"

A regular database is a filing cabinet with labeled folders — you need the exact label to find something. A vector store is a librarian who understands your question and finds the most relevant books, even if your words don't exactly match the titles.

Why ChromaDB?

Open Source

Free, Apache 2.0 license. No vendor lock-in.

Lightweight

Runs in-process, no separate server needed. pip install chromadb.

LangChain Integration

First-class support via langchain-chroma package.

Metadata Filtering

Combine similarity search with metadata filters for precise results.

Vector Store Type Best For

ChromaDB Architecture

Your Application LangChain · Python code
ChromaDB Client Collections · Add · Query · Delete
Storage Vectors · Documents · Metadata · IDs

Each document stores:

  • ID — unique identifier
  • Embedding — vector representation
  • Document — original text
  • Metadata — source, page, date, etc.

Two modes:

  • In-memory — fast, ephemeral (for labs)
  • Persistent — saved to disk (for production)

Both use the same API. Just change one setting.

Collections & Metadata

import chromadb

# Create a persistent ChromaDB client
client = chromadb.PersistentClient(path="./chroma_db")

# Create a collection (like a table in SQL)
collection = client.get_or_create_collection("company_docs")

# Add documents with metadata
collection.add(
    documents=["Refund within 30 days of purchase",
              "Free shipping on orders above Rs 500"],
    metadatas=[{"source": "policy.pdf", "page": 3},
              {"source": "policy.pdf", "page": 7}],
    ids=["doc1", "doc2"]
)
Metadata is powerful. You can filter search results by source, page number, date, category — any key-value pair you attach. This lets you build precise retrieval: "Find refund info from the 2024 policy document only."

Querying ChromaDB

# Basic similarity search
results = collection.query(
    query_texts=["How do I return a product?"],
    n_results=3
)

print(results["documents"])  # [["Refund within 30 days..."]]
print(results["metadatas"])  # [[{"source": "policy.pdf", "page": 3}]]
print(results["distances"])  # [[0.34]] (lower = more similar)

# Search with metadata filter
results = collection.query(
    query_texts=["shipping info"],
    n_results=3,
    where={"source": "policy.pdf"}
)

Notice: you searched with "How do I return a product?" and it found "Refund within 30 days" — different words, same meaning. That's the power of embeddings.

Text Splitting: Why and How

Documents are too long to fit in one embedding

from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,      # max characters per chunk
    chunk_overlap=50,    # overlap between chunks (preserves context)
    separators=["\n\n", "\n", " ", ""]  # split priority
)

text = """Our refund policy allows returns within 30 days. Items must be in original packaging. Contact support for return labels. Refunds are processed within 5-7 business days."""

chunks = splitter.split_text(text)
print(len(chunks))  # Number of chunks created

Too large chunks (5000+)

Dilutes the meaning — embeddings become vague. Retrieval returns irrelevant content.

Right-sized chunks (200-1000)

Each chunk has focused meaning. Retrieval is precise. Overlap preserves boundary context.

Building RAG Pipelines

Ingestion · Query Processing · Context Retrieval · Response Generation

LangChain + ChromaDB

The complete ingestion pipeline in code

from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_community.embeddings import HuggingFaceEmbeddings
from langchain_chroma import Chroma

# 1. Load
loader = PyPDFLoader("company_policy.pdf")
pages = loader.load()  # List of Document objects (one per page)

# 2. Split
splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(pages)

# 3. Embed + Store
vectorstore = Chroma.from_documents(
    documents=chunks,
    embedding=HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2"),
    persist_directory="./chroma_db"
)
Three steps: Load → Split → Store. LangChain's Chroma.from_documents() handles embedding and storing in one call. The persist_directory saves the vector store to disk so you don't re-embed every time.

Creating a Retriever

The bridge between your vector store and your chain

# Create a retriever from the vector store
retriever = vectorstore.as_retriever(
    search_type="similarity",  # or "mmr" for diversity
    search_kwargs={"k": 3}    # return top 3 results
)

# Use it directly
docs = retriever.invoke("What is the refund policy?")

for doc in docs:
    print(doc.page_content)  # the text
    print(doc.metadata)      # {"source": "policy.pdf", "page": 3}
A retriever is like a research assistant. You ask a question, and they go to the library (vector store), find the most relevant books and pages, and bring them back to you. You then use those references to write your answer.

The RAG Chain

Combining retrieval with generation

from langchain_groq import ChatGroq
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

llm = ChatGroq(model="llama-3.3-70b-versatile")

prompt = ChatPromptTemplate.from_template("""Answer based on the context below. If the context doesn't contain the answer, say "I don't know." Context: {context} Question: {question} Answer:""")

# The RAG chain
rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt | llm | StrOutputParser()
)

answer = rag_chain.invoke("What is the refund policy?")
print(answer)

What Happens Inside the RAG Chain?

Step Component Input Output
1 RunnablePassthrough "What is the refund policy?" Passes query unchanged
2 Retriever "What is the refund policy?" 3 relevant document chunks
3 Prompt Template {context: docs, question: query} Formatted prompt with context injected
4 LLM (ChatGroq) Formatted prompt AIMessage grounded in context
5 StrOutputParser AIMessage Clean answer string
This is the same LCEL pipe pattern from Session 3, with one addition: the retriever fetches context before the prompt. The LLM never sees documents it wasn't given — grounded by design.

Response Generation with Citations

Tell the user where the answer came from

prompt = ChatPromptTemplate.from_template("""Answer using ONLY the context below. Include the source and page number for each fact you cite. Context: {context} Question: {question} Answer (with citations):""")

# Format documents with source info
def format_docs(docs):
    return "\n\n".join(
        f"[Source: {d.metadata['source']}, Page {d.metadata.get('page', '?')}]\n{d.page_content}"
        for d in docs
    )

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt | llm | StrOutputParser()
)
By including source information in the context and asking the LLM to cite its sources, you get answers like: "Returns are accepted within 30 days (policy.pdf, page 3)." This builds trust and allows users to verify answers.
