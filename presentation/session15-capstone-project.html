01

Phase 1: Architecture Design

Lab 01 · Define components, data flows, dependencies

This is the most important phase. Encourage participants to spend real time here rather than jumping into code. A good architecture diagram and dependency map will save hours of debugging later. Ask them to identify every component, draw the data flow from client request to response, and define what happens when each dependency fails.
Phase 1 — Lab 01

Architecture Design


Define Components

  • List every service your system needs
  • Identify which sessions each component comes from
  • Map dependencies between components

Draw Data Flows

  • Request path: Client → API → Agent → Tools → Response
  • Observability path: App → LangFuse → Dashboard
  • Trace path: App → LangFuse → Dashboard

Plan Dependencies

  • Which services start first?
  • What happens if ChromaDB is down?
  • What happens if the LLM API times out?

Deliverable

  • Architecture diagram (code or drawing)
  • Component inventory list
  • Startup order and dependency map

Good architecture is the foundation. Spend time here — it saves debugging time later.

Phase 2: MCP Server

Lab 02 · Build MCP server with tools from Session 13

Participants will build an MCP server using FastMCP from Session 13. The server should register at least two or three tools -- typically a document search tool backed by ChromaDB, a calculator or data analysis tool, and optionally a web lookup tool. Remind them to test the server standalone before wiring it into the agent. The tool decorator pattern from Session 13 labs should be fresh in their minds.
Phase 2 — Lab 02

MCP Server Implementation


FastMCP Server

  • Register tools using @mcp.tool() decorator
  • Expose resources with @mcp.resource()
  • Define prompt templates with @mcp.prompt()

Tool Registry

  • Document search tool (ChromaDB)
  • Calculator / data analysis tool
  • Web lookup tool

Phase 3: API Endpoint

Lab 03 · FastAPI endpoint from Session 12

The FastAPI application is the front door. Participants should implement the POST /agent/query endpoint with Pydantic validation, health and readiness probes, and proper error handling with specific HTTP status codes from Session 12. Remind them: if the front door is broken, nothing else matters. Get a basic endpoint returning a hardcoded response first, then wire in the real agent.
Phase 3 — Lab 03

FastAPI Application


Endpoints

Request Handling

  • Async request processing

Production Features

  • Request timeout handling

The FastAPI application is the front door of your system. Every request enters here, gets validated, routed to the agent, and returns a structured response. If the front door is broken, nothing else matters.
04

Phase 4: Instrumentation

Lab 04 · LangFuse traces from Session 11

This phase adds the observability layer from Sessions 10 and 11. Participants wire in the LangFuse CallbackHandler for automatic trace capture, add structured JSON logging with trace_id and token counts, and set up cost tracking per request. The goal is that after this phase, every single request through the system produces a visible trace in the LangFuse dashboard with full latency and cost breakdowns.
Phase 4 — Lab 04

Observability Instrumentation

  • Collect user feedback scores

Structured Logging

  • Log levels: DEBUG, INFO, WARN, ERROR
  • Request/response payload logging

LangFuse Metrics

05

Phase 5: Health & Monitoring

Lab 05 · Probes + metrics from Session 12

Health probes are what Kubernetes uses to decide whether to restart your pod or remove it from the load balancer. Participants should implement a liveness probe that returns 200 if the process is alive, and a readiness probe that checks whether the LLM API is reachable and ChromaDB is connected. Remind them of the three-probe model from Session 12 and that a process can be alive but not ready.
Phase 5 — Lab 05

Health Probes & Monitoring


Liveness Probe

GET /health

  • Returns 200 if app is alive
  • Checks: process running, no deadlock
  • Failure: process restart

Readiness Probe

GET /ready

  • Returns 200 if ready for traffic
  • Checks: DB connected, LLM reachable
  • Failure: removed from load balancer

LangFuse Tracing

CallbackHandler

  • Auto-instrumented LLM calls
  • Traces sent to LangFuse
  • Visualized in LangFuse dashboard

Phase 6: Deployment Config

Lab 06 · Containerization and deployment manifests

This phase covers the deployment configuration -- uvicorn settings, environment variable management with .env files, and process startup sequencing. In the Codespace environment, participants will use Python process management rather than Docker containers due to resource constraints. Remind them that API keys must never be hardcoded -- use python-dotenv and the .env.example pattern from Session 12.
Phase 6 — Lab 06

Deployment Configuration


uvicorn Configuration

  • Host, port, and worker settings
  • Graceful shutdown with signal handlers
  • Health check endpoint
  • Environment variable configuration

Python Process Management

  • App + mock LangFuse + ChromaDB in-process
  • psutil resource monitoring
  • Python startup sequencing
  • Local file persistence

Environment Config

  • psutil for resource monitoring
  • Python dotenv for config loading
  • .env files for config and secrets
  • Async HealthChecker for all services

Security

  • API keys in Secrets, not env vars
  • Read-only filesystem where possible
  • Network policies for traffic control
  • Image scanning before deploy
07

Phase 7: Testing

Lab 07 · Comprehensive test plan

Testing AI applications requires a different mindset from traditional testing. Participants should write unit tests for Pydantic models and utility functions (deterministic), mock LLM tests for agent logic (repeatable), and integration tests for the full API flow. Emphasize testing the error paths: what happens when the LLM times out, when a tool fails, when input validation rejects a request? These edge cases are where production systems break.
Phase 7 — Lab 07

Testing Strategy


End-to-End Tests
Full request through agent to response
↓
Integration Tests
API + Agent + Tools working together
↓
Unit Tests
Individual functions, tools, and parsers

What to Test

  • Happy path: valid query → correct response
  • Error path: invalid input → proper error message
  • Timeout path: slow LLM → graceful timeout
  • Tool failure: MCP server down → fallback behavior

Tools & Frameworks

  • pytest for unit and integration tests
  • httpx for async API testing
  • Mock LLM responses for deterministic tests
  • Health endpoint smoke tests
08

Phase 8: Integration Challenge

Lab 08 · Full production deployment

This is the final challenge -- wire all seven phases together into one working system. The success criteria is end-to-end: send a query, the agent processes it, tools are called via MCP, a response comes back, the trace appears in LangFuse, and health probes pass. Remind participants to focus on getting a working end-to-end flow first, then optimize. A working but simple system scores better than a complex but broken one.
