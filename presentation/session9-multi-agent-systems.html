01

Multi-Agent Architectures

From single graphs to cooperating agent systems

Why Multi-Agent?

Single agents hit limits — multi-agent systems scale intelligence

Single Agent

  • One LLM handles everything
  • Prompt grows with complexity
  • Hard to maintain as scope grows
  • Single point of failure

Multi-Agent

  • Specialized agents per domain
  • Each agent has focused prompt
  • Easy to add/remove capabilities
  • Fault-tolerant with fallbacks
A single employee trying to handle HR, finance, and tech support vs. a team of specialists each handling their domain — the team scales better.

Architecture Patterns Overview

Pattern Topology Control Best For
Supervisor/Worker Hub & spoke Central supervisor routes tasks Clear task delegation, known domains
Peer-to-Peer Mesh / ring Agents communicate directly Collaborative reasoning, brainstorming
Handoff Sequential chain Agent decides when to pass control Multi-step workflows, escalation
Hierarchical Tree Multi-level supervisors Complex orgs, nested delegation
Choose based on task structure: known domains → Supervisor, creative tasks → Peer-to-Peer, sequential processes → Handoff.

Request: {state['request']} Reply: HANDLE if simple, HANDOFF:specialist_name if complex""" response = llm.invoke(prompt) text = response.content.strip() if "HANDOFF:" in text: target = text.split("HANDOFF:")[1].strip() return {"handoff_to": target, "audit": [f"Handing off to {target}"]} return {"response": text, "handoff_to": "done", "audit": ["Handled by triage"]} def route_handoff(state) -> str: return state["handoff_to"] # "tech_specialist", "hr_specialist", "done" graph.add_conditional_edges("triage", route_handoff, { "tech_specialist": "tech_agent", "hr_specialist": "hr_agent", "done": "finalize", })

Architecture Decision Guide

Scenario Pattern Why
UniGPS support desk with HR, Tech, Finance domains Supervisor/Worker Clear domains, central routing
Report writing: research, draft, review cycles Peer-to-Peer Iterative collaboration
Customer support with L1 → L2 → L3 escalation Handoff Sequential escalation
Enterprise with department heads managing sub-teams Hierarchical Nested delegation
Start with Supervisor/Worker — it covers 80% of real-world multi-agent use cases. Add Peer-to-Peer or Handoff when needed.

Decomposition Strategies

By Domain

"Onboard a new employee"

  • HR agent → create employee record
  • IT agent → set up laptop & accounts
  • Finance agent → add to payroll
  • Facilities agent → assign desk

By Phase

"Analyze and respond to complaint"

  • Phase 1: Sentiment analysis agent
  • Phase 2: Root cause analysis agent
  • Phase 3: Solution drafting agent
  • Phase 4: Response review agent

By Capability

"Generate quarterly report"

  • Data agent → pull numbers from DB
  • Analysis agent → compute trends
  • Writer agent → draft narrative
  • Chart agent → create visualizations

Parallel vs Sequential

Key design decision

  • Independent tasks → parallel
  • Tasks with dependencies → sequential
  • LangGraph handles both via edges
  • Parallel = fan-out + reducer merge

Conflict Resolution

When agents disagree on the answer

Priority-Based

Domain expert overrides generalist. E.g., the finance agent's budget number takes precedence over the general agent's estimate.

Voting / Majority

Run 3 agents, take majority answer. Works well for classification and binary decisions.

Arbitrator Agent

A dedicated agent reviews conflicting outputs and makes the final call with reasoning.

Human Escalation

When agents can't agree, pause the workflow and ask a human reviewer (HITL).

Conflict Resolution — Code

Arbitrator Pattern
def detect_conflict(state): outputs = state["worker_outputs"] # Check if agents agree categories = [o["category"] for o in outputs] if len(set(categories)) == 1: return {"has_conflict": False, "agreed_answer": categories[0]} return {"has_conflict": True, "audit": [f"Conflict: agents said {categories}"]} def arbitrator(state): prompt = f"""Two agents disagree. Their outputs: {state['worker_outputs']} Analyze both and pick the better answer with reasoning.""" response = llm.invoke(prompt) return {"final_response": response.content} def route_conflict(state) -> str: return "arbitrator" if state["has_conflict"] else "finalize"

Collaboration Summary

Decompose

Break complex tasks by domain, phase, or capability. Use LLM or rule-based splitting.

Aggregate

Use LLM synthesis for text, reducers for structured data, voting for decisions.

Resolve Conflicts

Priority, voting, arbitrator, or human escalation when agents disagree.

The three pillars of collaboration: decompose the task, let workers execute, aggregate results, and resolve any conflicts.

Production Agent Patterns

Building reliable multi-agent systems at scale

Agent Specialization & Roles

Each agent has a clear, focused responsibility

Why Specialize?

  • Focused prompts = better quality
  • Agent-specific tools per domain
  • Easier to test individually
  • Can use different LLMs per agent

Specialist Design

  • Prompt: Domain-specific system prompt
  • Tools: Only tools the agent needs
  • Model: Match model to complexity
  • Guardrails: Input/output validation
# Different models for different agents fast_llm = ChatGroq(model="llama-3.1-8b-instant") # triage (fast, cheap) smart_llm = ChatGroq(model="llama-3.3-70b-versatile") # complex analysis

Common Agent Roles

Role Responsibility Model Choice Tools
Router / Triage Classify and route requests Fast, small model None (LLM only)
Domain Specialist Handle specific domain tasks Large, capable model Domain-specific APIs, DBs
Reviewer / QA Validate outputs before delivery Large model with eval skills Validation schemas
Aggregator Combine multi-worker results Large model for synthesis None (LLM only)
A hospital: the receptionist (router) triages patients to the right specialist (cardiologist, orthopedist), and the chief doctor (reviewer) reviews treatment plans before discharge.

Load Balancing Across Agents

Distributing work to avoid bottlenecks

Round-Robin

Distribute requests evenly across equivalent worker agents. Simple but effective for uniform workloads.

def round_robin(state): workers = ["w1", "w2", "w3"] idx = state["req_count"] % len(workers) return {"assigned": workers[idx]}

Capability-Based

Route to the agent best equipped for the task. Different agents have different strengths.

def capability_route(state): if state["complexity"] > 7: return {"assigned": "expert"} return {"assigned": "junior"}
In LangGraph, load balancing happens in the routing function — the same conditional edge mechanism you already know, just with smarter assignment logic.

Scaling Multi-Agent Systems

Horizontal Scaling

  • Multiple instances of the same worker
  • Stateless agents scale easily
  • State managed via external checkpointer
  • PostgresSaver for shared state across instances

Cost Management

  • Fast model for routing (8B params)
  • Large model only for complex tasks (70B)
  • Cache common responses
  • Circuit breaker saves tokens on failures

Observability

  • Audit trail per request (state reducer)
  • Per-agent latency tracking
  • Error rates per worker
  • LangFuse / OpenTelemetry integration

Testing Strategy

  • Unit test each agent independently
  • Integration test the full graph
  • Mock LLM responses for determinism
  • Replay from checkpoints for regression

Production Checklist

1. Each agent has a single responsibility with a focused prompt

2. Use the right-sized model for each agent role

3. Implement fallback chains — primary → fallback → template

4. Track every decision in an audit trail via reducers

5. Use persistent checkpointing (PostgresSaver) in production

6. Add observability — latency, errors, token usage per agent

7. Test agents independently and as a system

Production multi-agent = specialization + fallbacks + observability. Start simple, add agents as needs grow.

In the Supervisor/Worker pattern, what is the supervisor's primary job?
A Execute all the domain-specific logic directly
B Analyze the request and route it to the right worker agent
C Store all state in the checkpointer

Why B? The supervisor is the orchestrator — it analyzes incoming requests, classifies them, and routes to specialized workers using conditional edges. Workers do the domain-specific work. This separation of concerns is what makes the pattern powerful.

Why B? Peer-to-peer shines when agents build on each other's work iteratively. A researcher gathers facts, a writer drafts, a reviewer critiques, and the cycle repeats. Supervisor/Worker is better for clear domain separation (A). Both support audit trails (D).

Answer: Question 5
In a production multi-agent system, why would you use a fast 8B model for the router agent and a large 70B model for specialist agents?
A 8B models are more accurate at classification tasks
B Routing is simple (classification), while specialists need deep reasoning — optimizes cost and latency
C LangGraph requires different model sizes per node
D Only 70B models support tool calling
Why B? This is the right-sizing principle: routing is a simple classification task that a small, fast model handles well. Specialist agents need deeper reasoning for complex domain tasks. Using a fast model for routing reduces cost and latency without sacrificing quality where it matters. LangGraph doesn't require different models (C) — it's a design choice.
