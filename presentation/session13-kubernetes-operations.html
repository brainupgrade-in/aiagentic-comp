Debugging & Troubleshooting

When things go wrong with your AI stack on K8s

The K8s Debugging Toolkit

Command What It Shows When to Use
kubectl get pods Pod names, status, restarts, age First check — is anything unhealthy?
kubectl describe pod NAME Events, conditions, probe failures Pod stuck in Pending/CrashLoop
kubectl logs NAME Container stdout/stderr output Application errors, stack traces
kubectl logs NAME --previous Logs from the crashed container CrashLoopBackOff (see why it died)
kubectl exec -it NAME -- bash Shell inside a running container Network tests, file inspection
kubectl top pods CPU/memory usage per pod Resource issues, OOMKill risk

Debugging Flow: Step by Step

Follow this sequence when an AI pod is unhealthy

1
kubectl get pods
What's the status? Running, Pending, CrashLoopBackOff?
2
kubectl describe pod NAME
Check Events section at the bottom for errors
3
kubectl logs NAME
Read application output — Python tracebacks, import errors
4
kubectl exec -it NAME -- bash
Get inside: check files, test DNS, curl services
5
kubectl top pods
Is it running out of memory or CPU?

Pod Status Reference

Status Meaning Action
Running Pod is running normally Check if READY column shows expected count (e.g., 1/1)
Pending Pod cannot be scheduled describe → check node resources, node selectors, PVC binding
CrashLoopBackOff Container keeps crashing and restarting logs --previous → see crash reason (import error, bad config)
ImagePullBackOff Cannot pull the container image Check image name, tag, registry auth (imagePullSecrets)
OOMKilled Container exceeded memory limit Increase resources.limits.memory or optimize app
Init:0/1 Init container hasn't completed logs NAME -c init-container-name

CrashLoopBackOff — The Most Common Issue

Your container starts, crashes, restarts, crashes again...

$ kubectl get pods NAME READY STATUS RESTARTS AGE unigps-agent-7f4d9-abc12 0/1 CrashLoopBackOff 5 3m $ kubectl logs unigps-agent-7f4d9-abc12 --previous ModuleNotFoundError: No module named 'langchain_groq' # Missing dependency in requirements.txt! $ kubectl describe pod unigps-agent-7f4d9-abc12 Events: Warning BackOff Back-off restarting failed container

Common Causes

  • Missing Python dependency
  • Wrong CMD in Dockerfile
  • Missing environment variable (GROQ_API_KEY)
  • Port already in use
  • Config file not found

Fix Pattern

  • logs --previous → read the error
  • Fix the image or config
  • Rebuild & push image
  • kubectl rollout restart deploy/NAME
  • Or fix ConfigMap/Secret and restart

ImagePullBackOff — Image Problems

$ kubectl get pods NAME READY STATUS RESTARTS AGE unigps-agent-7f4d9-xyz99 0/1 ImagePullBackOff 0 2m $ kubectl describe pod unigps-agent-7f4d9-xyz99 Events: Warning Failed Failed to pull image "unigps-agent:2.0": rpc error: manifest for unigps-agent:2.0 not found

Wrong Image Name

Typo in image name or tag. Check spec.containers[].image

Private Registry

Missing imagePullSecrets. Create a docker-registry Secret.

Tag Doesn't Exist

Image was never pushed, or tag was overwritten. Check your registry.

# Create pull secret for private registry kubectl create secret docker-registry regcred \ --docker-server=registry.example.com \ --docker-username=user \ --docker-password=pass # Reference in pod spec spec: imagePullSecrets: - name: regcred

Pending Pods — Cannot Schedule

$ kubectl get pods NAME READY STATUS RESTARTS AGE unigps-agent-7f4d9-qrs44 0/1 Pending 0 5m $ kubectl describe pod unigps-agent-7f4d9-qrs44 Events: Warning FailedScheduling 0/3 nodes are available: 3 Insufficient memory

Common Causes

  • Insufficient resources — no node has enough CPU/memory
  • PVC not bound — no PersistentVolume available
  • Node selector mismatch — no node has the required label
  • Taints/tolerations — pod can't tolerate node taints

Fixes

  • Reduce resources.requests
  • Add more nodes to the cluster
  • Check PVC with kubectl get pvc
  • Remove node selector or label the node

AI-Specific Debugging

Problems unique to LangChain / LLM agent workloads

OOMKilled (Memory)

Embedding models or large LLM responses exhaust memory.

  • kubectl describe pod → "OOMKilled"
  • Fix: increase limits.memory
  • Monitor: kubectl top pods

Probe Timeout (LLM Latency)

LLM API calls take 10-30s; liveness probe thinks pod is dead.

  • Fix: increase timeoutSeconds on liveness probe
  • Use a separate /health endpoint (not the LLM endpoint)
  • Set periodSeconds > typical LLM response time

Secret Not Mounted

Agent starts but LLM calls fail: "API key not found".

  • kubectl exec -- env | grep GROQ
  • Check: envFrom reference matches Secret name
  • Check: Secret exists in same namespace

DNS Resolution Failed

Agent can't reach Redis or ChromaDB by service name.

  • kubectl exec -- nslookup redis-svc
  • Check: Service exists with correct selector
  • Check: target pod labels match Service selector

Debug Command Cheat Sheet

# See all resources at once kubectl get pods,svc,deploy,sts,pvc -o wide # Check events across the namespace (most recent first) kubectl get events --sort-by='.lastTimestamp' # Stream logs from all pods of a deployment kubectl logs -f deploy/unigps-agent --all-containers # Check env vars inside a running pod kubectl exec deploy/unigps-agent -- env | sort # Test service connectivity from inside a pod kubectl exec deploy/unigps-agent -- curl -s redis-svc:6379 kubectl exec deploy/unigps-agent -- curl -s chromadb-svc:8000/api/v1/heartbeat # Check resource usage (needs metrics-server) kubectl top pods --sort-by=memory kubectl top nodes # Force restart all pods of a deployment (new pods, same config) kubectl rollout restart deployment/unigps-agent

Debugging Summary

1. Always start with kubectl get pods — check status and restart count

2. CrashLoopBackOff → logs --previous to see the crash reason

3. ImagePullBackOff → check image name, tag, and registry credentials

4. Pending → describe for scheduling failures (resources, PVC, labels)

5. OOMKilled → increase limits.memory, monitor with top pods

6. AI-specific: check Secrets mounted, DNS resolves, probe timeouts > LLM latency

Scaling & High Availability

Keep your AI stack running reliably under any load

Two Dimensions of Scaling

Horizontal Scaling (HPA)

  • Add more pods (replicas)
  • Automatic based on CPU/memory
  • Best for stateless services (AI agent)
  • Fast: new pods start in seconds

+Pod

Vertical Scaling

  • Give pods more CPU/memory
  • Manual: update resource limits
  • Required for memory-hungry models
  • Limited by node capacity

For AI agents: horizontal scaling (more replicas) handles traffic spikes. For embedding models: vertical scaling (more memory) handles larger models.

HPA Tuning for AI Workloads

hpa.yaml (production-tuned)
apiVersion: autoscaling/v2 kind: HorizontalPodAutoscaler metadata: name: agent-hpa spec: scaleTargetRef: apiVersion: apps/v1 kind: Deployment name: unigps-agent minReplicas: 2 # Always at least 2 for HA maxReplicas: 10 # Cap costs metrics: - type: Resource resource: name: cpu target: type: Utilization averageUtilization: 70 # Scale up when avg CPU > 70% - type: Resource resource: name: memory target: type: Utilization averageUtilization: 80 # Also scale on memory behavior: scaleDown: stabilizationWindowSeconds: 300 # Wait 5 min before scaling down

HPA Best Practices for AI

Setting Recommendation Why
minReplicas 2 or more Never go to 1 — no HA if that pod crashes
maxReplicas Based on budget Cap costs; 10 agent pods = 10x LLM API calls
CPU target 60-80% Leave headroom for LLM response processing spikes
scaleDown window 300s (5 min) Prevent flapping (scale up/down repeatedly)
resources.requests Set accurately HPA calculates % of requests — wrong requests = wrong scaling
Do not use HPA on StatefulSets like ChromaDB or Redis unless you have proper data replication. Scaling stateful services requires careful planning.

Pod Disruption Budget (PDB)

Protect your AI agent during cluster maintenance

Without PDB

Cluster admin drains a node for maintenance.

  • All 3 agent pods might be on that node
  • K8s evicts all 3 at once
  • Zero pods serving traffic until new ones start
  • Downtime!

With PDB

PDB tells K8s: "keep at least 2 pods running".

  • K8s evicts 1 pod at a time
  • Waits for replacement to be Ready
  • Then evicts the next
  • Zero downtime during maintenance!
pdb.yaml
apiVersion: policy/v1 kind: PodDisruptionBudget metadata: name: agent-pdb spec: minAvailable: 2 # Always keep at least 2 pods running selector: matchLabels: app: agent

PDB Configuration Options

minAvailable

minAvailable: 2 # OR minAvailable: "60%"

"At least 2 pods (or 60%) must stay running during disruption."

maxUnavailable

maxUnavailable: 1 # OR maxUnavailable: "25%"

"At most 1 pod (or 25%) can be unavailable during disruption."

Use minAvailable or maxUnavailable (not both). For 3 agent replicas, minAvailable: 2 means K8s can only evict 1 pod at a time during node maintenance.

Multi-Replica Best Practices

Component Replicas Notes
AI Agent (FastAPI) 3+ (HPA: 2–10) Stateless — scale freely; use PDB for HA
Redis (cache) 1 Single replica OK for cache; use Redis Sentinel/Cluster for HA
ChromaDB (vectors) 1 Single replica with PVC; no built-in replication yet
Ingress Controller 2+ HA for the entry point; managed by cloud provider or helm chart
Scale what's stateless (agent) aggressively. Scale what's stateful (databases) conservatively. A fast agent with 10 replicas still depends on 1 Redis — don't bottleneck at the data layer.

Production Readiness Checklist

Reliability

  • Readiness + liveness probes configured
  • Resource requests & limits set
  • PDB for disruption protection
  • minReplicas ≥ 2 for agent

Scalability

  • HPA configured with CPU/memory
  • Scale-down stabilization window
  • maxReplicas capped for cost control
  • Stateful services sized correctly

Observability

  • Structured logging (JSON)
  • kubectl top pods baseline
  • Alerts on restarts, OOMKills
  • Dashboard for HPA activity

Security

  • Secrets for API keys (not ConfigMap)
  • Non-root container user
  • Network policies (if needed)
  • Image scanning in CI/CD

Scaling & HA Summary

1. Horizontal scaling (HPA) for stateless services; vertical for memory-hungry models

2. HPA tuning: minReplicas ≥ 2, scaleDown window = 300s, accurate requests

3. Pod Disruption Budget — protect pods during node maintenance

4. Multi-replica: agent = 3+ replicas; Redis/ChromaDB = 1 (single with PVC)

5. Production checklist: probes, resources, PDB, HPA, logging, secrets

Answer: Question 1
A pod is in CrashLoopBackOff. What command shows why it crashed?
A kubectl get pods -o wide
B kubectl logs POD --previous
C kubectl top pods
D kubectl scale deployment --replicas=0
Why B? The --previous flag shows logs from the previous (crashed) container instance. Since the pod keeps restarting, the current container may have no useful logs yet. --previous shows the stack trace or error that caused the crash.

B The Ingress configuration

Answer: Question 2
A pod shows status Pending for several minutes. What is the most likely first thing to check?
A The container's application logs
B The Ingress configuration
C The Events section in kubectl describe pod
D The HPA current replica count
Why C? A Pending pod hasn't started yet — there are no application logs to check. kubectl describe pod shows the Events section at the bottom, which reveals why the scheduler can't place the pod: insufficient resources, unbound PVC, no matching nodes, etc.
Question 3 of 5
Your AI agent pod keeps getting OOMKilled. What should you do?
A Delete and recreate the pod
B Increase resources.limits.memory in the Deployment
C Remove the liveness probe
D Decrease the number of replicas to free up memory
Answer: Question 3
Your AI agent pod keeps getting OOMKilled. What should you do?
A Delete and recreate the pod
B Increase resources.limits.memory in the Deployment
C Remove the liveness probe
D Decrease the number of replicas to free up memory
Why B? OOMKilled means the container's actual memory usage exceeded its resources.limits.memory. The fix is to increase the limit (e.g., from 512Mi to 1Gi). Also use kubectl top pods to monitor actual usage and set limits with headroom. Deleting the pod would just restart it with the same limit — it would OOMKill again.

Answer: Question 4
What does a Pod Disruption Budget (PDB) protect against?
A Application bugs causing containers to crash
B Too many pods being evicted at once during voluntary disruptions like node maintenance
C External DDoS attacks on the Ingress
D Memory leaks in Python applications
Why B? PDBs protect against voluntary disruptions: node drain, cluster upgrades, or scaling operations. With minAvailable: 2, K8s won't evict more than 1 pod at a time from a 3-replica Deployment. PDBs don't help with involuntary disruptions (node crashes) or application bugs.

Answer: Question 5
Why should HPA's minReplicas be at least 2 for a production AI agent?
A Kubernetes requires a minimum of 2 pods for any Deployment
B Having 2 pods doubles the application's throughput at all times
C If one pod crashes or is evicted, the other keeps serving traffic with zero downtime
D HPA cannot calculate metrics with only 1 pod running
Why C? High availability means no single point of failure. With minReplicas: 1, if that single pod crashes, restarts, or is evicted during a node drain, there are zero pods serving traffic until a replacement starts. With minReplicas: 2, one pod can always handle requests while the other recovers.
