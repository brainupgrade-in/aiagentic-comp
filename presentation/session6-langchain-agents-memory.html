Agent Types

ReAct · Function Calling · Custom Agents

Chains vs Agents

What makes an agent different from a chain?

Chain (Session 3-4)

  • Fixed sequence: prompt → LLM → parser
  • Always runs the same steps in the same order
  • No decision-making at runtime
  • Great for predictable workflows

prompt | llm | parser

Agent (Today)

  • Dynamic: LLM decides what to do next
  • Can use tools, loop, and change strategy
  • Reasons about which action to take
  • Handles unexpected situations

Think → Act → Observe → Repeat

A chain is like a recipe — follow steps 1, 2, 3, done. An agent is like a chef who reads the recipe but improvises based on what ingredients are available, adjusts seasoning after tasting, and tries a different approach if something burns.

ReAct Agents

Reasoning + Acting in a loop

Think
What should I do?
→
Act
Call a tool
→
Observe
Read the result
→
Decide
Done or loop?

Example: "What's the weather in Bangalore and should I carry an umbrella?"

Think: I need weather data → Act: Call weather_tool("Bangalore") → Observe: "24°C, 70% rain chance" → Decide: I have enough info → Answer: "Yes, carry an umbrella — 70% chance of rain."

ReAct is the most common agent pattern. The LLM reasons about what tool to call, acts by calling it, then observes the result before deciding the next step.

ReAct Agent in LangChain

from langchain_groq import ChatGroq
from langchain_core.tools import tool
from langgraph.prebuilt import create_react_agent

# Define tools
@tool
def weather(city: str) -> str:
    """Get current weather for a city."""
    return {"Bangalore": "24°C, 70% rain"}.get(city, "Unknown")

# Create the agent
llm = ChatGroq(model="llama-3.3-70b-versatile")
agent = create_react_agent(llm, tools=[weather])

# Run it
result = agent.invoke(
    {"messages": [("human", "Weather in Bangalore?")]}
)
print(result["messages"][-1].content)
create_react_agent from langgraph.prebuilt is the modern way to build agents. You give it an LLM and tools — it handles the Think → Act → Observe loop automatically.

Function-Calling Agents

The LLM natively decides which tool to call

How It Works

  • Tools are described as JSON schemas to the LLM
  • LLM outputs a structured tool call (not free text)
  • The framework executes the tool and returns the result
  • LLM uses the result to form a final answer

Why It's Better

  • More reliable than text-based parsing
  • LLM sees tool descriptions and parameter types
  • Structured output — no regex parsing needed
  • Modern LLMs (Llama 3, GPT-4) support this natively
# LLM sees this tool description:
# {"name": "weather", "description": "Get weather for a city",
# "parameters": {"city": {"type": "string"}}}

# LLM responds with structured call (not free text):
# {"tool": "weather", "args": {"city": "Bangalore"}}

Binding Tools to an LLM

from langchain_groq import ChatGroq
from langchain_core.tools import tool

@tool
def calculator(expression: str) -> str:
    """Calculate a math expression. Input: a math expression like '2 + 3'."""
    return str(eval(expression))

llm = ChatGroq(model="llama-3.3-70b-versatile")

# Bind tools — LLM now knows about calculator
llm_with_tools = llm.bind_tools([calculator])

# LLM decides to call the tool
response = llm_with_tools.invoke("What is 17 * 28 + 55?")
print(response.tool_calls)
# [{"name": "calculator", "args": {"expression": "17 * 28 + 55"}}]
bind_tools is like handing a calculator to a student before an exam. The student (LLM) now knows the calculator is available and can choose to use it when a math question comes up — but they still decide when and how.

Agent Types Compared

Agent Type How It Decides Best For LangChain API
ReAct Reasons step-by-step in a loop Multi-step tasks needing planning create_react_agent()
Function-Calling LLM natively outputs tool calls Single-step tool use, structured output llm.bind_tools()
Custom Your own logic for routing and decisions Complex workflows, domain-specific rules LangGraph StateGraph
Start with ReAct (create_react_agent) — it covers 80% of use cases. Use function-calling for simple tool use. Build custom agents with LangGraph when you need full control over the decision flow.

Tool Integration

Built-in Tools · Custom Tools · Multi-Tool Orchestration

What Are Tools?

Functions the agent can call to interact with the world

Information Tools

Search the web, query databases, fetch APIs, read documents

Action Tools

Send emails, create files, update records, call external services

Computation Tools

Calculate math, run code, process data, transform formats

A tool is simply a Python function with a description that tells the LLM what it does and what arguments it needs. The LLM reads the description and decides when to call it.

Creating Tools with @tool

The simplest way to define a tool

from langchain_core.tools import tool

@tool
def get_order_status(order_id: str) -> str:
    """Check the status of a customer order. Input: order ID like 'ORD-001'."""
    orders = {"ORD-001": "Shipped, arriving tomorrow",
              "ORD-002": "Processing, 2 days"}
    return orders.get(order_id, "Order not found")

# What the LLM sees:
print(get_order_status.name)        # "get_order_status"
print(get_order_status.description)  # "Check the status of..."
print(get_order_status.args_schema)  # {"order_id": {"type": "string"}}
The docstring is critical — it's how the LLM understands what the tool does. Write clear, specific descriptions. Include examples of valid inputs. The LLM will use this description to decide when and how to call your tool.

Multi-Tool Agent

Agent with several tools to choose from

from langchain_core.tools import tool
from langgraph.prebuilt import create_react_agent

@tool
def weather(city: str) -> str:
    """Get current weather for a city."""
    return {"Bangalore": "24°C, Rain", "Mumbai": "32°C, Sunny"}.get(city, "Unknown")

@tool
def calculator(expression: str) -> str:
    """Calculate a math expression like '15 * 7 + 3'."""
    return str(eval(expression))

@tool
def get_time() -> str:
    """Get the current date and time."""
    from datetime import datetime
    return datetime.now().strftime("%A, %B %d at %I:%M %p")

agent = create_react_agent(llm, tools=[weather, calculator, get_time])
# The agent picks the right tool for each question automatically!

Multi-Tool Orchestration

The agent chains tool calls when needed

Query: "Is it warmer in Bangalore or Mumbai? Show the difference in Fahrenheit."

Step 1: Think → I need weather for both cities
Step 2: Call weather("Bangalore") → "24°C"
Step 3: Call weather("Mumbai") → "32°C"
Step 4: Think → Now convert and compare
Step 5: Call calculator("(32-24) * 9/5") → "14.4"
Step 6: Answer: "Mumbai is warmer. Difference is 14.4°F."

The agent autonomously decides to call three tools in sequence: two weather lookups and one calculation. It reasons about the results and composes a final answer. You didn't hardcode this flow — the LLM figured it out.

Tool Design Best Practices

Do

  • Write clear, specific docstrings
  • Include example inputs in the description
  • Use type hints for all parameters
  • Return helpful error messages
  • Keep tools focused — one tool, one job

Don't

  • Write vague descriptions ("does stuff")
  • Create one mega-tool that does everything
  • Forget to handle edge cases
  • Give tools destructive power without safeguards
  • Use more than 5-7 tools per agent (LLM gets confused)

Memory & Conversation Management

Buffer Memory · Summary Memory · Session Persistence

Why Memory Matters

LLMs are stateless — every call starts fresh

Without Memory

User: My name is Raj
Bot: Nice to meet you, Raj!

User: What is my name?
Bot: I don't know your name.

Each call is independent. The LLM forgot everything.

With Memory

User: My name is Raj
Bot: Nice to meet you, Raj!

User: What is my name?
Bot: Your name is Raj!

Previous messages are included in every call. Context preserved.

Memory Types

Buffer Memory

Store the entire conversation history. Every message is kept and sent to the LLM each time.

Simple but grows fast

Best for: short conversations (5-10 turns)

Summary Memory

Use an LLM to summarize older messages. Keeps recent messages + a summary of earlier ones.

Token-efficient

Best for: long conversations (10+ turns)

Window Memory

Keep only the last N messages. Older messages are dropped entirely.

Fixed size, simple

Best for: stateless tasks with brief context

Buffer Memory = a tape recorder that records everything. Summary Memory = a note-taker who writes key points and discards details. Window Memory = a whiteboard with limited space — old notes get erased.

Conversation Buffer Memory

The simplest approach: store all messages

from langchain_groq import ChatGroq
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

llm = ChatGroq(model="llama-3.3-70b-versatile")

# The "memory" is just a list of messages
memory = [SystemMessage(content="You are a helpful assistant. Be concise.")]

def chat(user_msg):
    memory.append(HumanMessage(content=user_msg))
    response = llm.invoke(memory)
    memory.append(AIMessage(content=response.content))
    return response.content

print(chat("My name is Raj"))    # "Nice to meet you, Raj!"
print(chat("What is my name?"))  # "Your name is Raj!"
print(f"Messages in memory: {len(memory)}")  # 5
At its core, memory is just appending messages to a list and passing the full list to the LLM every time. The LLM sees the entire conversation history and can reference anything said earlier.

Conversation Summary Memory

Summarize older messages to save tokens

from langchain_groq import ChatGroq
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

llm = ChatGroq(model="llama-3.3-70b-versatile")
MAX_MESSAGES = 6  # keep last 6 messages, summarize the rest

def summarize_old_messages(messages):
    """Use the LLM to summarize older messages."""
    old_text = "\n".join(m.content for m in messages)
    summary = llm.invoke(
        f"Summarize this conversation in 2 sentences:\n{old_text}"
    )
    return SystemMessage(content=f"Summary of earlier conversation: {summary.content}")

def chat_with_summary(memory, user_msg):
    memory.append(HumanMessage(content=user_msg))
    if len(memory) > MAX_MESSAGES:
        summary = summarize_old_messages(memory[1:-MAX_MESSAGES])
        memory[:] = [memory[0], summary] + memory[-MAX_MESSAGES:]
    response = llm.invoke(memory)
    memory.append(AIMessage(content=response.content))
    return response.content

Session Management

Persisting conversations across restarts

In-Memory (Lab/Dev)

Messages stored in a Python list. Lost when the process restarts.

sessions = {}
sessions["user-1"] = [msg1, msg2]

Persistent (Production)

Messages stored in a database. Survive restarts and scale to many users.

# LangGraph checkpoint
SqliteSaver(db_path)
PostgresSaver(conn_string)
For production, use LangGraph checkpointers (SQLite, PostgreSQL) to persist conversation state. Each user gets a thread_id that maps to their conversation history. The agent can resume any conversation from where it left off.

Multi-User Session Pattern

from langgraph.prebuilt import create_react_agent
from langgraph.checkpoint.memory import MemorySaver

# Create agent with memory
memory = MemorySaver()
agent = create_react_agent(llm, tools=[weather], checkpointer=memory)

# User A's conversation
config_a = {"configurable": {"thread_id": "user-A"}}
agent.invoke({"messages": [("human", "I live in Bangalore")]}, config=config_a)
agent.invoke({"messages": [("human", "What's the weather here?")]}, config=config_a)
# ^ Agent remembers "here" = Bangalore from the previous message

# User B's separate conversation (isolated)
config_b = {"configurable": {"thread_id": "user-B"}}
agent.invoke({"messages": [("human", "Weather in Mumbai?")]}, config=config_b)
Each thread_id gets its own isolated conversation history. User A's messages are never seen by User B's agent. This is how production chatbots handle thousands of concurrent users with a single agent instance.
