Deployment Strategies

Rolling updates, auto-scaling, and traffic routing

Rolling Updates in Depth

Zero-downtime deployments for AI services

spec: replicas: 3 strategy: type: RollingUpdate rollingUpdate: maxSurge: 1 # At most 1 extra pod during update maxUnavailable: 0 # Never fewer than 3 pods available
v1.0
3 pods
→
Transition
3 old + 1 new
→
Transition
2 old + 2 new
→
v2.0
3 pods

maxSurge: 1

Creates at most 1 extra pod. Total = replicas + maxSurge. Keeps resource usage predictable.

maxUnavailable: 0

Never have fewer than replicas pods available. Guarantees zero downtime during updates.

Rollback: Undo a Bad Deployment

When the new version breaks, go back instantly

# Check deployment history kubectl rollout history deployment/unigps-agent # Rollback to previous version kubectl rollout undo deployment/unigps-agent # Rollback to a specific revision kubectl rollout undo deployment/unigps-agent --to-revision=2 # Watch the rollout progress kubectl rollout status deployment/unigps-agent
K8s keeps a history of Deployment revisions. If your new AI model version returns bad results, kubectl rollout undo switches back in seconds — not hours.

Horizontal Pod Autoscaler (HPA)

Automatically scale pods based on CPU, memory, or custom metrics

What HPA Does

  • Monitors pod CPU/memory usage
  • Scales up when load increases
  • Scales down when load decreases
  • Keeps resource usage within target

When to Use for AI

  • API traffic spikes (batch requests)
  • Variable LLM query volume
  • Business hours vs off-hours load
  • Cost optimization (scale down at night)
Low Load
2 pods
→
CPU > 70%
HPA triggers
→
High Load
6 pods
→
CPU < 40%
HPA cooldown
→
Low Load
2 pods

HPA Configuration

hpa.yaml
apiVersion: autoscaling/v2 kind: HorizontalPodAutoscaler metadata: name: agent-hpa spec: scaleTargetRef: apiVersion: apps/v1 kind: Deployment name: unigps-agent minReplicas: 2 # Never below 2 (HA) maxReplicas: 10 # Never above 10 (cost control) metrics: - type: Resource resource: name: cpu target: type: Utilization averageUtilization: 70 # Scale when CPU > 70%
HPA requires resources.requests on your pods. Without requests, K8s cannot calculate utilization percentages. Also needs metrics-server installed in the cluster.

Ingress — HTTP Routing

Route external HTTP traffic to internal Services by hostname or path

Internet

(nginx / traefik)

/vectors → chromadb-svc:8000
/ → frontend-svc:3000

Why Ingress over LoadBalancer?

  • One external IP for all services
  • Path-based routing (/api, /vectors)
  • Host-based routing (api.unigps.in)
  • TLS/SSL termination

LoadBalancer = 1 per Service

  • Each gets its own external IP
  • Expensive on cloud ($$$ per LB)
  • No path/host routing
  • Fine for simple single-service setups

Ingress Manifest

ingress.yaml
apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: ai-stack-ingress annotations: nginx.ingress.kubernetes.io/rewrite-target: / spec: ingressClassName: nginx rules: - host: api.unigps.in http: paths: - path: / pathType: Prefix backend: service: name: agent-svc port: number: 8000 tls: # HTTPS with cert-manager - hosts: - api.unigps.in secretName: api-tls-cert

Deployment Strategies Summary

1. Rolling updates — zero-downtime deployments with maxSurge/maxUnavailable

2. Rollback — kubectl rollout undo for instant version revert

3. HPA — auto-scale pods on CPU/memory (needs metrics-server + requests)

4. Ingress — single entry point with path/host-based routing + TLS

5. Ingress over LoadBalancer — one IP, multiple services, cost-effective

Configuration & Storage

PersistentVolumes, PVCs, and StatefulSets for AI data

Why Persistent Storage?

The Problem

  • Pods are ephemeral — data dies with the pod
  • Container filesystem is temporary
  • Pod restart = all data lost

What about ChromaDB's vector embeddings?
Redis data? Uploaded documents?

The Solution

  • PersistentVolume (PV) — actual storage
  • PersistentVolumeClaim (PVC) — request for storage
  • Data survives pod restarts and reschedules

PVC attaches storage to pods.
Think of it as a "storage reservation".

PV = a parking garage (real storage). PVC = a parking ticket (reservation). Your pod presents the ticket to get a spot. Even if you leave and come back, your reserved spot is still there.

PersistentVolumeClaim

Most clusters have dynamic provisioning — you only need a PVC

pvc.yaml
apiVersion: v1 kind: PersistentVolumeClaim metadata: name: chroma-data spec: accessModes: - ReadWriteOnce # One pod can write at a time storageClassName: standard # Cloud provider's default class resources: requests: storage: 10Gi # Request 10 GB of disk
Access Mode Abbrev Use Case
ReadWriteOnce RWO Single pod read/write (databases, ChromaDB)
ReadOnlyMany ROX Multiple pods read-only (shared model files)
ReadWriteMany RWX Multiple pods read/write (shared uploads — needs NFS)

Mounting a PVC in a Pod

deployment.yaml (excerpt)
spec: containers: - name: chromadb image: chromadb/chroma:latest volumeMounts: - name: chroma-storage mountPath: /chroma/chroma # Where ChromaDB stores data volumes: - name: chroma-storage persistentVolumeClaim: claimName: chroma-data # References the PVC above

→

chroma-data (10Gi)
→

AWS EBS / GCE PD
Pod restarts? Data is safe on the PV. Pod moves to another node? The PV follows (on cloud providers). ChromaDB vectors persist across any pod lifecycle event.

StatefulSet — For Stateful Apps

When you need stable identity + persistent storage per pod

Deployment (Stateless)

  • Pods get random names (agent-7f4d9)
  • Pods are interchangeable
  • Shared PVC (or no storage)
  • Use for: AI agent, API, workers

StatefulSet (Stateful)

  • Pods get stable names (redis-0, redis-1)
  • Pods are not interchangeable
  • Unique PVC per pod (volumeClaimTemplates)
  • Use for: databases, ChromaDB, Redis
chromadb-0 ↔ PVC-0 (10Gi)
chromadb-1 ↔ PVC-1 (10Gi)
chromadb-2 ↔ PVC-2 (10Gi)
Each pod gets its own
persistent volume.
Pod names are stable:
always chromadb-0, 1, 2.

StatefulSet Manifest

statefulset.yaml (key fields)
apiVersion: apps/v1 kind: StatefulSet metadata: name: chromadb spec: serviceName: chromadb-headless # Required: headless service for DNS replicas: 1 selector: matchLabels: app: chromadb template: metadata: labels: app: chromadb spec: containers: - name: chromadb image: chromadb/chroma:latest volumeMounts: - name: data mountPath: /chroma/chroma volumeClaimTemplates: # Auto-creates PVC per pod - metadata: name: data spec: accessModes: ["ReadWriteOnce"] resources: requests: storage: 10Gi

Storage Patterns for AI Stack

Component Type Storage Access Mode
AI Agent (FastAPI) Deployment None (stateless) —
Redis (cache) Deployment or StatefulSet 1–5 Gi (optional) RWO
ChromaDB (vectors) StatefulSet 10–50 Gi RWO
Model files (shared) PVC mounted in pods 1–20 Gi ROX (shared read)
Document uploads PVC or object storage Variable RWX or S3
Stateless services (agent) use Deployments — no storage needed. Stateful services (ChromaDB, Redis) use StatefulSets with PVCs so data survives pod restarts.

Configuration & Storage Summary

1. Pod data is ephemeral — use PVCs for anything you want to keep

2. PersistentVolumeClaim — requests storage; cloud auto-provisions the PV

3. ReadWriteOnce for databases; ReadOnlyMany for shared models

4. StatefulSet — stable pod names + unique PVC per pod

5. AI agent = Deployment (stateless); ChromaDB/Redis = StatefulSet (stateful)

Deploying ChromaDB on K8s

Full AI stack: Agent + Redis + ChromaDB with persistent storage

Full AI Stack Architecture

Ingress api.unigps.in → agent-svc:8000
Agent (×3) Deployment + LoadBalancer/Ingress + HPA
Redis (×1) Deployment + ClusterIP + optional PVC
ChromaDB (×1) StatefulSet + ClusterIP + PVC (10Gi)
ConfigMap + Secret Shared configuration and API keys

Apply order: ConfigMap/Secret → PVCs → Redis → ChromaDB → Agent → Ingress

ChromaDB StatefulSet

chromadb-statefulset.yaml
apiVersion: apps/v1 kind: StatefulSet metadata: name: chromadb spec: serviceName: chromadb-headless replicas: 1 selector: matchLabels: { app: chromadb } template: metadata: labels: { app: chromadb } spec: containers: - name: chromadb image: chromadb/chroma:latest ports: - containerPort: 8000 resources: requests: { memory: "512Mi", cpu: "500m" } limits: { memory: "2Gi", cpu: "1000m" } readinessProbe: httpGet: { path: /api/v1/heartbeat, port: 8000 } initialDelaySeconds: 10 livenessProbe: httpGet: { path: /api/v1/heartbeat, port: 8000 } initialDelaySeconds: 30 volumeMounts: - name: data mountPath: /chroma/chroma volumeClaimTemplates: - metadata: { name: data } spec: accessModes: ["ReadWriteOnce"] resources: requests: { storage: 10Gi }

ChromaDB Services

StatefulSets need a headless Service for DNS + a regular Service for access

Headless Service (DNS)

apiVersion: v1 kind: Service metadata: name: chromadb-headless spec: clusterIP: None selector: app: chromadb ports: - port: 8000

clusterIP: None = headless.
Gives each pod a DNS name:
chromadb-0.chromadb-headless

ClusterIP Service (Access)

apiVersion: v1 kind: Service metadata: name: chromadb-svc spec: type: ClusterIP selector: app: chromadb ports: - port: 8000 targetPort: 8000

Agent connects via:
CHROMA_URL=http://chromadb-svc:8000

Deployment Order

Apply manifests in dependency order

# 1. Configuration (no dependencies) kubectl apply -f configmap.yaml -f secret.yaml # 2. Storage-backed services first (others depend on them) kubectl apply -f redis-deployment.yaml -f redis-svc.yaml kubectl apply -f chromadb-headless-svc.yaml kubectl apply -f chromadb-statefulset.yaml -f chromadb-svc.yaml # 3. Application (depends on Redis + ChromaDB) kubectl apply -f agent-deployment.yaml -f agent-svc.yaml # 4. External access (depends on agent Service) kubectl apply -f ingress.yaml # 5. Auto-scaling (depends on Deployment) kubectl apply -f hpa.yaml # Verify everything is running kubectl get all

Verify Your Deployment

# Check all resources kubectl get pods,svc,deploy,statefulset,pvc # Check agent is healthy kubectl exec -it deploy/unigps-agent -- curl localhost:8000/health # Check ChromaDB is reachable from agent kubectl exec -it deploy/unigps-agent -- curl chromadb-svc:8000/api/v1/heartbeat # Check Redis is reachable kubectl exec -it deploy/unigps-agent -- curl -s redis-svc:6379 || echo "Redis OK (TCP)" # Tail agent logs kubectl logs -f deploy/unigps-agent # Check HPA status kubectl get hpa
Always verify inter-service connectivity after deployment. Use kubectl exec to test DNS resolution from inside a pod — this confirms Services and network policies are working.

Complete Manifest File Structure

k8s/ ├── configmap.yaml # LOG_LEVEL, REDIS_URL, CHROMA_URL ├── secret.yaml # GROQ_API_KEY (base64) ├── agent-deployment.yaml # 3 replicas, probes, envFrom ├── agent-svc.yaml # ClusterIP or LoadBalancer ├── redis-deployment.yaml # 1 replica, probes ├── redis-svc.yaml # ClusterIP (redis-svc:6379) ├── chromadb-headless-svc.yaml # Headless for StatefulSet DNS ├── chromadb-statefulset.yaml # 1 replica, PVC template, probes ├── chromadb-svc.yaml # ClusterIP (chromadb-svc:8000) ├── ingress.yaml # api.unigps.in → agent-svc └── hpa.yaml # Auto-scale agent 2→10 pods

11 manifests. One kubectl apply -f k8s/ deploys the entire AI stack.

Full Stack Deployment Checklist

1. ConfigMap + Secret — config and API keys separated from images

2. Agent Deployment — 3 replicas, probes, resources, envFrom

3. Redis Deployment — ClusterIP service, session/cache data

4. ChromaDB StatefulSet — headless service, PVC for persistent vectors

5. Ingress — TLS, path routing, single external endpoint

6. HPA — auto-scale agent pods on CPU utilization

7. Verify with kubectl get all + kubectl exec connectivity tests

Answer: Question 1
What does maxUnavailable: 0 in a RollingUpdate strategy guarantee?
A No pods will ever be created during the update
B The update will happen instantly instead of gradually
C The number of available pods never drops below the desired replica count
D The deployment cannot be rolled back once started
Why C? maxUnavailable: 0 means K8s will not terminate any old pod until a new one is ready. Combined with maxSurge: 1, the update proceeds by creating one new pod, waiting for it to pass readiness, then terminating one old pod — guaranteeing zero downtime.

A A LoadBalancer Service attached to the Deployment
B Resource requests defined on pods and metrics-server installed
C A ConfigMap with CPU thresholds for each pod
D An Ingress controller with rate limiting enabled
Answer: Question 2
What does the Horizontal Pod Autoscaler (HPA) require to calculate CPU utilization?
A A LoadBalancer Service attached to the Deployment
B Resource requests defined on pods and metrics-server installed
C A ConfigMap with CPU thresholds for each pod
D An Ingress controller with rate limiting enabled
Why B? HPA calculates utilization as a percentage of the pod's resources.requests.cpu. Without requests, there's no denominator — HPA can't compute a percentage. The metrics-server collects the actual CPU/memory usage from each node's kubelet.

Answer: Question 3
What happens to data on a PersistentVolumeClaim (PVC) when its pod is deleted?
A The data is deleted along with the pod
B The data persists — a new pod can mount the same PVC
C The data is automatically backed up to S3
D The PVC is converted to a ConfigMap for safekeeping
Why B? That's the entire purpose of PVCs — data outlives the pod. When a StatefulSet pod restarts or moves to another node, it re-mounts the same PVC. ChromaDB's vector embeddings survive pod crashes, updates, and rescheduling. PVCs are only deleted when you explicitly kubectl delete pvc.

Answer: Question 4
Why use a StatefulSet instead of a Deployment for ChromaDB?
A StatefulSets are faster at starting containers
B StatefulSets provide stable pod names and unique persistent volumes per pod
C StatefulSets support more replicas than Deployments
D StatefulSets don't require a container image
Why B? ChromaDB stores vector embeddings on disk. A StatefulSet guarantees: (1) stable pod names like chromadb-0 that don't change on restart, (2) volumeClaimTemplates that create a unique PVC per pod, and (3) pods are started/stopped in order. Deployments create random pod names and share PVCs — not suitable for databases.

Answer: Question 5
In a full AI stack deployment, why should Redis and ChromaDB be deployed before the AI agent?
A Kubernetes requires alphabetical deployment order
B The agent depends on Redis and ChromaDB — deploying it first would cause connection errors
C Redis and ChromaDB need more CPU, so they must be deployed first to reserve resources
D The agent Deployment YAML includes Redis and ChromaDB configurations
Why B? The agent's readiness probe may check connectivity to Redis and ChromaDB. If they're not running, the agent pod's probe fails repeatedly. While K8s will eventually sort it out (the agent will become ready once dependencies start), deploying in dependency order avoids unnecessary restarts, error logs, and faster overall startup.
