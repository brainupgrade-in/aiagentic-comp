FastAPI Integration

Building REST APIs for your AI agents

Why FastAPI for AI Agents?

FastAPI Strengths

  • Async-native — perfect for LLM calls
  • Auto-docs — Swagger UI at /docs
  • Pydantic models — request/response validation
  • Streaming — StreamingResponse for LLM output
  • Fast — built on Starlette & uvicorn

Agent API Needs

  • Accept user requests via HTTP
  • Route to LangGraph workflows
  • Stream tokens as they're generated
  • Handle errors gracefully
  • Health checks for monitoring
FastAPI is the reception desk of your agent system — it takes requests from the outside world, passes them to the right team inside, and delivers the response back.

API Architecture

Client (Browser / Mobile / CLI) HTTP requests
↓
FastAPI Layer Routes, validation, auth
↓
LangGraph Agent StateGraph, nodes, edges
↓
LLM Provider (Groq / OpenAI) API calls for inference

Basic Agent Endpoint

POST /api/support
from fastapi import FastAPI from pydantic import BaseModel app = FastAPI(title="UniGPS Agent API") class SupportRequest(BaseModel): employee_name: str request: str class SupportResponse(BaseModel): category: str response: str audit: list[str] @app.post("/api/support", response_model=SupportResponse) async def handle_support(req: SupportRequest): result = agent_graph.invoke({ "employee_name": req.employee_name, "request": req.request, "audit": [], }) return SupportResponse( category=result["category"], response=result["final_response"], audit=result["audit"], )

Async Request Handling

LLM calls are I/O-bound — async lets you serve many requests concurrently

import asyncio @app.post("/api/support") async def handle_support(req: SupportRequest): # run_in_executor moves blocking LLM call off the event loop loop = asyncio.get_event_loop() result = await loop.run_in_executor( None, # default thread pool lambda: agent_graph.invoke({ "employee_name": req.employee_name, "request": req.request, "audit": [], }) ) return {"response": result["final_response"]}

Without async

1 request blocks the server for 2-5 seconds while the LLM responds. Other users wait.

With async

Server handles many concurrent requests. While one LLM call waits, others are processed.

Streaming Responses

Send tokens to the client as they're generated — no waiting for full response

from fastapi.responses import StreamingResponse async def stream_agent(request_text: str): # LangGraph stream() yields state updates per node for event in agent_graph.stream({"request": request_text, "audit": []}): for node_name, output in event.items(): if "response" in output: yield f"data: {output['response']}\n\n" yield "data: [DONE]\n\n" @app.post("/api/support/stream") async def stream_support(req: SupportRequest): return StreamingResponse( stream_agent(req.request), media_type="text/event-stream", )
Streaming uses Server-Sent Events (SSE). The client sees tokens appear in real-time instead of waiting 3-5 seconds for the complete response.

Error Handling & Validation

from fastapi import HTTPException from pydantic import BaseModel, Field class SupportRequest(BaseModel): employee_name: str = Field(..., min_length=1, max_length=100) request: str = Field(..., min_length=5, max_length=1000) @app.post("/api/support") async def handle_support(req: SupportRequest): try: result = agent_graph.invoke({...}) return {"response": result["final_response"]} except Exception as e: raise HTTPException( status_code=500, detail={"error": "Agent processing failed", "message": str(e)} ) @app.get("/health") async def health_check(): return {"status": "healthy", "agent": "ready"}

Pydantic Validation

Auto-validates input. Returns 422 with details for bad requests.

HTTPException

Return proper HTTP status codes (400, 404, 500) with error messages.

Health Check

GET /health for load balancers and monitoring systems.

Production API Structure

Endpoint Method Purpose
/health GET Health check for load balancers
/api/support POST Submit a support request, get full response
/api/support/stream POST Submit request, receive SSE streaming response
/api/support/{thread_id} GET Retrieve state of a conversation by thread ID
/docs GET Auto-generated Swagger UI (built into FastAPI)
FastAPI auto-generates interactive API documentation at /docs from your Pydantic models. No extra work needed.

FastAPI Summary

1. Define Pydantic models for request/response validation

2. Use async def + run_in_executor for non-blocking LLM calls

3. Add StreamingResponse for real-time token delivery

4. Use HTTPException for proper error codes

5. Include /health endpoint for monitoring

6. Get free Swagger docs at /docs

Testing AI Applications

Making non-deterministic systems testable

Why AI Testing Is Different

Traditional Testing

  • Deterministic: same input = same output
  • Fast: ms per test
  • Free: no API costs
  • Isolated: no external dependencies

AI Agent Testing

  • Non-deterministic: LLM responses vary
  • Slow: 1-5s per LLM call
  • Costly: tokens per test run
  • External: depends on LLM provider
Testing a calculator is easy: 2+2 always equals 4. Testing an AI agent is like testing a conversation — you verify the structure and intent, not the exact words.

Testing Strategy

Unit Tests Fast, mocked LLM
↓
Integration Tests Full graph, mocked LLM
↓
End-to-End Tests Real LLM, fewer tests

Unit (80%)

Individual nodes, routing functions, reducers. Mock all LLM calls.

Integration (15%)

Full graph execution. Mock LLM but test real routing and state flow.

E2E (5%)

Smoke tests with real LLM. Verify happy path works.

Unit Testing Agent Nodes

pytest
def test_supervisor_classifies_hr(): # Test the routing function directly — no LLM needed state = {"request": "I need sick leave", "assigned_to": "hr"} result = route_to_worker(state) assert result == "hr" def test_finalize_formats_response(): state = { "category": "tech", "worker_output": "Jira ticket created", } result = finalize(state) assert "TECH" in result["final_response"] assert "UniGPS" in result["final_response"] def test_quality_check_rejects_short(): state = {"worker_output": "OK"} result = qa_check(state) assert result["error"] # should flag "too short"
Test routing functions, formatters, validators, and reducers directly — these are pure functions that don't need an LLM.

Mocking LLM Responses

Replace real LLM calls with predictable, instant responses

from unittest.mock import patch, MagicMock def test_hr_worker_with_mock_llm(): # Create a mock that returns a predictable response mock_response = MagicMock() mock_response.content = "Your leave request has been processed." with patch("my_agent.llm") as mock_llm: mock_llm.invoke.return_value = mock_response state = {"request": "I need leave", "employee_name": "Priya"} result = hr_worker(state) assert "leave" in result["worker_output"].lower() assert result["error"] == "" mock_llm.invoke.assert_called_once() # verify LLM was called

Why Mock?

Tests run in milliseconds instead of seconds. No API costs. Deterministic results every time.

What to Verify

LLM was called with correct prompt. Output is correctly processed. Errors are handled.

Integration Testing Workflows

def test_full_graph_hr_flow(): # Mock all LLM calls in the graph mock_response = MagicMock() mock_response.content = "hr" # supervisor classifies as HR with patch("my_agent.llm") as mock_llm: mock_llm.invoke.return_value = mock_response result = app.invoke({ "request": "I need leave", "audit": [], }) # Verify the entire flow worked assert result["category"] == "hr" assert len(result["audit"]) >= 3 # supervisor + worker + finalize assert "final_response" in result def test_fallback_on_error(): # Simulate LLM failure with patch("my_agent.llm") as mock_llm: mock_llm.invoke.side_effect = Exception("API timeout") result = app.invoke({"request": "test", "audit": []}) assert result["fallback_used"] == True assert result["final_response"] # still got a response!

Test Fixtures & Factories

import pytest @pytest.fixture def sample_state(): """Standard test state that all tests can reuse.""" return { "employee_name": "Test User", "request": "I need help", "category": "", "confidence": 0, "worker_output": "", "error": "", "audit": [], } def make_state(**overrides): """Factory: create state with custom fields.""" defaults = {"request": "test", "audit": [], "error": ""} return {**defaults, **overrides} # Usage in tests def test_with_fixture(sample_state): result = supervisor(sample_state) assert "assigned_to" in result def test_with_factory(): state = make_state(request="server down", category="tech") result = tech_worker(state) assert result["worker_output"]

Testing Best Practices

Practice How Why
Mock LLM calls unittest.mock.patch Fast, free, deterministic
Test routing separately Call routing functions directly Pure functions, easy to test
Test error paths side_effect = Exception(...) Verify fallback chains work
Use fixtures @pytest.fixture + factories Consistent, reusable test data
Test API endpoints TestClient from FastAPI Verify HTTP layer works

Performance Optimization

Making AI agents fast and cost-effective

Where Time Is Spent

Typical agent request latency breakdown

LLM calls
80-90% of total time
Network
5-10%
Graph logic
<5%
LLM calls dominate latency. Optimization means: fewer LLM calls, faster models for simple tasks, and caching repeated requests.

Caching Strategies

Response Cache

Cache full LLM responses for identical inputs. Hash the prompt as key.

from functools import lru_cache @lru_cache(maxsize=1000) def cached_classify(request: str): return llm.invoke( f"Classify: {request}" ).content

Embedding Cache

Cache vector embeddings for RAG queries. Embeddings are deterministic — same text = same vector.

from langchain.cache import InMemoryCache import langchain langchain.llm_cache = InMemoryCache()

Redis Cache (Production)

Distributed cache shared across API instances. Survives server restarts.

Semantic Cache

Cache similar (not identical) queries. Use embeddings to find near-matches.

Connection Pooling

Reuse connections instead of creating new ones per request

# BAD: creates a new LLM client per request @app.post("/api/support") async def handle(req: SupportRequest): llm = ChatGroq(model="llama-3.3-70b-versatile") # new connection every time! result = llm.invoke(req.request) # GOOD: shared client, initialized once at startup llm = ChatGroq(model="llama-3.3-70b-versatile") # created once @app.post("/api/support") async def handle(req: SupportRequest): result = llm.invoke(req.request) # reuses connection

LLM Client

Initialize once at module level. Share across all requests. Thread-safe by design.

Database Connections

Use connection pools for PostgresSaver and vector stores. Set pool_size based on expected concurrency.

Async Operations & Concurrency

import asyncio async def parallel_agent_calls(requests: list[str]): """Process multiple agent requests concurrently.""" loop = asyncio.get_event_loop() tasks = [ loop.run_in_executor(None, agent_graph.invoke, {"request": req, "audit": []}) for req in requests ] results = await asyncio.gather(*tasks) return results # Process 5 requests concurrently instead of sequentially # Sequential: 5 × 3s = 15s # Concurrent: ~3s (limited by slowest request)
LangGraph's invoke() is synchronous. Use run_in_executor to run multiple graphs concurrently. For LangGraph's async support, use ainvoke().

Model Right-Sizing

Match model size to task complexity

Task Model Latency Cost
Classification / routing 8B (fast) ~200ms Low
Simple Q&A 8B-13B ~300ms Low
Analysis / drafting 70B ~1-3s Medium
Complex reasoning 70B+ / GPT-4 ~3-8s High
# Different models per agent role router_llm = ChatGroq(model="llama-3.1-8b-instant") # fast, cheap worker_llm = ChatGroq(model="llama-3.3-70b-versatile") # accurate, slower

Performance Checklist

1. Cache repeated LLM calls (lru_cache, Redis, LangChain cache)

2. Right-size models — fast model for routing, large for analysis

3. Pool connections — initialize LLM clients once, share across requests

4. Async I/O — run_in_executor for blocking calls, asyncio.gather for parallel

5. Stream responses — start delivering tokens immediately

6. Monitor — track latency, token usage, and error rates per agent

Optimization priority: cache > model right-sizing > async > streaming. Each step gives diminishing returns, so start from the top.

Why is async def with run_in_executor important for FastAPI agent endpoints?
A It makes LLM responses more accurate
B It prevents blocking the event loop so other requests can be served while waiting for LLM
C It reduces the cost of LLM API calls

Why B? LLM calls take 1-5 seconds. Without async, the server is blocked during that time and can't serve other users. run_in_executor moves the blocking call to a thread pool, freeing the event loop to handle concurrent requests.

Answer: Question 5
What is the single biggest performance optimization for an AI agent API?
A Using a faster programming language like Rust
B Caching LLM responses for repeated/similar queries
C Adding more CPU cores to the server
D Minifying the Python source code
Why B? LLM calls account for 80-90% of latency. Caching eliminates the LLM call entirely for repeated queries — response time drops from seconds to milliseconds. The graph logic itself runs in under 5ms, so optimizing the language (A) or CPU (C) has negligible impact. Model right-sizing is the second-best optimization.
