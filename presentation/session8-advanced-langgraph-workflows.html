Complex Workflow Patterns

Multi-Branch · Parallel Execution · Advanced Routing

Key teaching points: Multi-branch graphs split work across parallel paths and join results. Parallel execution with Send() fans out work to multiple nodes simultaneously. Ask the audience: "Think of a use case where you need to run 3 analyses in parallel and merge the results — how would you design that graph?" Emphasize the importance of reducers when parallel nodes write to the same state field.

Multi-branch graphs fan out from a routing node and converge back to a shared node. This is the most common production pattern: classify → specialized handler → common finalization.

Fan-Out & Convergence

# Fan-out: one node routes to many
graph.add_conditional_edges(
    "classify",
    route_fn,
    {"hr": "handle_hr", "tech": "handle_tech", "finance": "handle_finance"}
)

# Convergence: all branches lead to one node
graph.add_edge("handle_hr", "format_response")
graph.add_edge("handle_tech", "format_response")
graph.add_edge("handle_finance", "format_response")
graph.add_edge("format_response", END)

Fan-Out

One node → multiple possible next nodes.
Uses add_conditional_edges() with routing function.

Convergence

Multiple nodes → one shared next node.
Uses multiple add_edge() calls pointing to the same target.

# Send "input" to three parallel nodes
graph.add_edge("input", "check_spam")
graph.add_edge("input", "check_sentiment")
graph.add_edge("input", "check_language")

# All three converge to "merge"
graph.add_edge("check_spam", "merge_results")
graph.add_edge("check_sentiment", "merge_results")
graph.add_edge("check_language", "merge_results")
When multiple edges leave a node, LangGraph can execute them in parallel. Use reducers (Annotated[list, add]) in the merge node so results accumulate rather than overwrite each other.

Parallel + Reducer Pattern

from typing import TypedDict, Annotated
from operator import add

class ReviewState(TypedDict):
    content: str
    checks: Annotated[list, add]  # ← reducer: each parallel node appends
    approved: bool

def check_spam(state) -> dict:
    return {"checks": [{"type": "spam", "passed": True}]}

def check_sentiment(state) -> dict:
    return {"checks": [{"type": "sentiment", "passed": True}]}

def merge_results(state) -> dict:
    all_passed = all(c["passed"] for c in state["checks"])
    return {"approved": all_passed}
Without a reducer on checks, only the last parallel node's result would survive. Always use Annotated[list, add] for fields that receive parallel writes.

State Management Deep Dive

Custom Reducers · Persistence Backends · State Recovery

Key teaching points: Custom reducers go beyond operator.add — sliding windows, deduplication, dictionary merging. Persistence backends: MemorySaver for development, SqliteSaver/PostgresSaver for production. Ask the audience: "Why is it important that switching persistence backends requires only one line of code change?" Answer: It decouples graph logic from infrastructure, making testing and deployment easier.

Beyond operator.add

Custom reducer functions

from typing import TypedDict, Annotated

# Custom reducer: keep only last N items
def keep_last_5(current: list, new: list) -> list:
    return (current + new)[-5:]

# Custom reducer: merge dictionaries
def merge_dicts(current: dict, new: dict) -> dict:
    return {**current, **new}

# Custom reducer: take maximum value
def take_max(current: int, new: int) -> int:
    return max(current, new)

class SmartState(TypedDict):
    messages: Annotated[list, keep_last_5]  # Sliding window
    metadata: Annotated[dict, merge_dicts]  # Merge updates
    max_score: Annotated[int, take_max]    # Keep highest
A reducer is any function (old_value, new_value) → combined_value. operator.add concatenates lists. You can write any logic: sliding windows, deduplication, merging, max/min, etc.

Built-in: add_messages Reducer

The standard way to handle chat history

from langgraph.graph import add_messages
from langchain_core.messages import HumanMessage, AIMessage

class ChatState(TypedDict):

# add_messages is smart:
# - Appends new messages to the list

def chatbot(state: ChatState) -> dict:

from langgraph.checkpoint.memory import MemorySaver
checkpointer = MemorySaver()

# Production — just swap the checkpointer!
from langgraph.checkpoint.sqlite import SqliteSaver
checkpointer = SqliteSaver.from_conn_string("checkpoints.db")

# Same compile() call — zero code changes in your graph!
app = graph.compile(checkpointer=checkpointer)

State Recovery & Resumption

Pick up exactly where you left off

# Scenario: Server restarts mid-workflow

# 1. Before restart: workflow was running on thread "order-42"
config = {"configurable": {"thread_id": "order-42"}}

# 2. After restart: reconnect to the same checkpointer
checkpointer = SqliteSaver.from_conn_string("checkpoints.db")
app = graph.compile(checkpointer=checkpointer)

# 3. Check where we left off
snapshot = app.get_state(config)
print(snapshot.values)  # Full state at last checkpoint
print(snapshot.next)    # ("process_payment",) — next node to run

# 4. Resume from where it stopped
result = app.invoke(None, config)  # ← continues from checkpoint
With a persistent checkpointer, your workflows survive server restarts, deployments, and crashes. The state is safely stored in the database. Just reconnect with the same thread_id and call invoke(None, config) to resume.

Error Handling & Retry Logic

Graceful Failures · Fallbacks · Circuit Breakers

Key teaching points: In production, LLM calls fail — timeouts, rate limits, bad responses. Best practice: catch errors inside nodes, store them in state, let conditional edges decide the next step. Ask the audience: "What should happen if an LLM call fails 3 times in a row?" Cover retry with exponential backoff, fallback to a cheaper model, and circuit breaker patterns.

Node-Level Error Handling

Wrap nodes with try/except for graceful failures

def call_llm(state) -> dict:
    try:
        response = llm.invoke(state["message"])
        return {
            "response": response.content,
            "error": None,
            "audit": ["LLM call successful"],
        }
    except Exception as e:
        return {
            "response": "",
            "error": str(e),
            "audit": [f"LLM error: {e}"],
        }
Store errors in state rather than raising exceptions. This lets downstream nodes make decisions: retry, use a fallback, or escalate. The workflow stays alive.

Error-Aware Routing

Route based on success or failure

def check_error(state) -> str:

Retry with Exponential Backoff

import time

class RetryState(TypedDict):
    message: str
    response: str
    error: str
    attempts: int
    max_attempts: int

def call_api(state) -> dict:
    attempt = state["attempts"] + 1
    try:
        response = llm.invoke(state["message"])
        return {"response": response.content, "error": "", "attempts": attempt}
    except Exception as e:
        time.sleep(2 ** attempt)  # Exponential backoff: 2s, 4s, 8s...
        return {"error": str(e), "attempts": attempt}

def should_retry(state) -> str:
    if not state["error"]: return "success"
    if state["attempts"] >= state["max_attempts"]: return "give_up"
    return "retry"    # ← cycle back!

graph.add_conditional_edges("call_api", should_retry,
    {"success": "process", "retry": "call_api", "give_up": "fallback"})

LLM Fallback Chain

Multi-Gate · User Input · Timeout · Escalation

Key teaching points: Beyond simple approve/reject — multi-gate workflows need multiple approvals in sequence. User input collection mid-workflow uses interrupt + update_state + resume. Multi-Gate Approval Workflows

Multiple pause points in one workflow

draft
→
GATE 1
review
→
approve
→
GATE 2
send
→
END
# Multiple interrupt points
app = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["review", "send"]  # ← TWO gates!
)

# Gate 1: pause before review
app.invoke(initial_state, config)  # Pauses at "review"
app.invoke(None, config)             # Resume, hits "send" gate

# Gate 2: pause before send
app.invoke(None, config)             # Resume, completes workflow

Collecting User Input Mid-Workflow

Pause, ask the user, inject their answer into state

# 1. Workflow reaches "collect_input" and pauses
app = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["process_answer"]
)

# 2. Run until pause — "ask_question" node sets state["question"]
app.invoke({"topic": "expense policy"}, config)

# 3. Read the question from state
snap = app.get_state(config)
question = snap.values["question"]
print(f"System asks: {question}")

# 4. User provides answer — inject it into state
user_answer = input("Your answer: ")
app.update_state(config, {"user_answer": user_answer})

# 5. Resume — "process_answer" now has the user's input
result = app.invoke(None, config)
This pattern turns any LangGraph workflow into an interactive conversation. The graph pauses, the system asks a question, the user answers, and the workflow continues with their input — all while maintaining full state.

Timeout & Escalation

What if the human doesn't respond?

import time
from datetime import datetime, timedelta

# Check if a paused workflow has timed out
def check_timeout(config, app, timeout_minutes=30):
    snap = app.get_state(config)
    if not snap.next:  # Not paused
        return False

    paused_at = snap.values.get("paused_at")
    if paused_at and datetime.now() - paused_at > timedelta(minutes=timeout_minutes):
        # Auto-escalate: update state and resume
        app.update_state(config, {
            "decision": "auto_escalated",
            "reason": "Timeout: no response in 30 minutes",
        })
        app.invoke(None, config)  # Resume with auto-escalation
        return True
    return False

Design Principles

1. State is the Source of Truth

Every decision, every error, every result lives in state. Nodes only communicate through state — never side channels.

2. Nodes Should Be Idempotent

Running a node twice with the same state should produce the same result. This makes retry and replay safe.

3. Always Include Guards

Every cycle needs a max-attempt limit. Every retry needs a backoff. Every HITL needs a timeout. No infinite loops.

4. Use Reducers for History

Current values overwrite. Historical data (logs, messages, audit trails) uses Annotated[list, add]. Mix both in one state.
