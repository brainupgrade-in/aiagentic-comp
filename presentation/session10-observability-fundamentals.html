01

Three Pillars of Observability

Metrics · Logs · Traces

Key teaching points: The three pillars are complementary, not competing. Metrics tell you "what" is happening (aggregates), Logs tell you "when and where" (events), Traces tell you "why" (request paths). Ask the audience: "When your production service slows down, what do you look at first — dashboards (metrics), log files, or traces?" Emphasize that most teams start with logs, but traces are the most powerful for debugging distributed systems.

Why Observability?

Monitoring tells you something is wrong. Observability tells you why.

Without Observability

  • Agent returns wrong answers — no idea why
  • Latency spikes — which service? which call?
  • Token costs increase — which prompts changed?
  • Users complain — can’t reproduce the issue

With Observability

  • Trace every request through agent → LLM → tools
  • Pinpoint which service adds latency
  • Track token usage per prompt version
  • Replay exact request path from traces
A car dashboard: speedometer (metrics), engine warning light (alerts), diagnostic port (traces), trip computer log (logs). You need all of them to understand how your car is really running.

The Three Pillars

METRICS

Quantitative Measurements

Numeric values over time. “How many? How fast? How much?”

Examples:
• Request count: 1,247/min
• Latency p99: 340ms
• CPU utilization: 72%
• Token usage: 45K/hour

LOGS

Discrete Events

Timestamped text records. “What happened?”

Examples:
• ERROR: ChromaDB connection refused
• INFO: Model loaded in 82s
• WARN: Rate limit approaching
• DEBUG: Tool call returned 3 results

TRACES

Request Flow

End-to-end path across services. “Where did time go?”

Examples:
• User → API → Agent → LLM (320ms)
• Agent → ChromaDB lookup (45ms)
• Agent → Tool call → Redis (12ms)
• Total request: 480ms

METRICS — Numbers Over Time

Aggregated, low-cardinality data that answers “is anything unusual happening?”

Metric Type Description AI Example
Counter Monotonically increasing value Total requests served, total tokens consumed
Gauge Value that goes up and down Active connections, queue depth, memory usage
Histogram Distribution of values in buckets Request latency (p50, p90, p99), token count per request
Summary Pre-calculated quantiles Model inference time percentiles
Metrics are cheap to store and fast to query. They’re your first line of defense — dashboards and alerts are built on metrics.

LOGS — Event Records

Rich, unstructured or structured text capturing discrete events

# Unstructured log (hard to parse)
2025-01-15 14:32:01 ERROR Failed to connect to ChromaDB at localhost:8000

# Structured log (machine-parseable, preferred)
{
  "timestamp": "2025-01-15T14:32:01Z",
  "level": "ERROR",
  "service": "agent-api",
  "message": "Failed to connect to ChromaDB",
  "target_host": "localhost:8000",
  "trace_id": "abc123def456",
  "retry_count": 3
}

Best Practices

  • Use structured logging (JSON)
  • Include trace_id to correlate with traces
  • Use consistent log levels (DEBUG, INFO, WARN, ERROR)
  • Don’t log sensitive data (API keys, PII)

AI-Specific Log Fields

  • model: which LLM was called
  • tokens_in/out: prompt/completion tokens
  • tool_calls: tools invoked by agent
  • retrieval_count: docs from RAG

Trace Concepts

  • Trace: End-to-end request journey
  • Span: One operation within a trace
  • Parent/Child: Spans nest hierarchically
  • Trace ID: Shared across all spans

Why Traces for AI?

  • See LLM call latency vs total time
  • Track agent reasoning steps
  • Identify which tool call is slow
  • Correlate with logs using trace_id

When to Use Which Pillar

Question Signal Example
“Is the system healthy right now?” METRICS Dashboard shows request rate, error rate, latency p99
“What went wrong at 3:42 PM?” LOGS Search logs for ERROR between 3:40–3:45 PM
“Why is this request slow?” TRACES Trace shows LLM call took 4.2s (vs usual 300ms)
“Are we burning tokens too fast?” METRICS Token counter shows 3x spike after prompt change
“Why did the agent pick the wrong tool?” TRACES + LOGS Trace shows reasoning steps, logs show tool parameters
The pillars are complementary, not competing. Metrics alert you, logs explain what happened, traces show you where and why.

AI Observability Challenges

AI systems have unique observability needs beyond traditional services

Non-Deterministic Outputs

Same input can produce different outputs. Need to track prompt versions, temperature, and model responses for reproducibility.

Multi-Step Reasoning

Agents make chains of decisions: plan → tool call → reflect → retry. Each step needs its own span in the trace.

Cost per Request

LLM calls have direct $ cost (tokens). Must track input/output tokens per call to manage spend and detect runaway agents.

Variable Latency

LLM calls range from 200ms to 30s. Traditional timeout/retry patterns need rethinking. Streaming adds complexity.

Section 01 Summary

Metrics

Numeric time-series: counters, gauges, histograms. Cheap to store, great for dashboards and alerts.

Logs

Discrete events with timestamps. Use structured JSON with trace_id for correlation.

Traces

End-to-end request flow via spans. Essential for understanding latency and multi-service paths.

All three pillars work together. Metrics detect problems, logs explain them, traces pinpoint them. AI systems need all three plus domain-specific signals (tokens, cost, reasoning steps).

OpenTelemetry

The Vendor-Neutral Standard

Key teaching points: OpenTelemetry (OTel) is the CNCF project that unifies metrics, logs, and traces under one API, SDK, and wire protocol (OTLP). Ask the audience: "Who here has used Prometheus, Jaeger, or Grafana? OTel is the common layer that feeds all of them." Key benefit: instrument once, export anywhere. No vendor lock-in. The Collector acts as a gateway with receivers, processors, and exporters.

What is OpenTelemetry?

A single framework for collecting all three observability signals

OpenTelemetry (OTel)

  • Vendor-neutral — not tied to any backend
  • CNCF project — 2nd most active after Kubernetes
  • One SDK for metrics, logs, and traces
  • Supports 11+ languages (Python, Go, Java, JS, ...)
  • Industry standard for instrumentation

Why OTel Matters

  • Instrument once, export to any backend
  • Switch from Jaeger to LangFuse? Change one config
  • No vendor lock-in on your instrumentation code
  • Community-maintained auto-instrumentation libraries
  • Consistent API across all languages
OTel is like USB-C for observability. Instead of every device having a proprietary cable, you have one universal connector that works with any charger (backend).

OTLP — The Universal Protocol

OpenTelemetry Protocol is the standard for transmitting telemetry data

gRPC (Default)

  • Port: 4317
  • Binary protobuf format
  • Most efficient
  • Bidirectional streaming

HTTP/protobuf

  • Port: 4318
  • Binary over HTTP POST
  • Firewall-friendly
  • Works through proxies

HTTP/JSON

  • Port: 4318
  • Human-readable
  • Easiest to debug
  • Least efficient

OTEL_RESOURCE_ATTRIBUTES="deployment.environment=production,service.version=2.0"

Auto vs Manual Instrumentation

Auto-Instrumentation

  • Zero code changes — just install packages
  • Instruments frameworks automatically (FastAPI, requests, SQLAlchemy)
  • Covers HTTP endpoints, database calls, external requests
  • Great starting point — get spans immediately
# Run with auto-instrumentation
opentelemetry-instrument \
  --service_name agent-api \
  python -m uvicorn main:app

Manual Instrumentation

  • Custom spans for business logic
  • Track LLM calls, tool usage, reasoning steps
  • Add custom attributes (tokens, model, cost)
  • Full control over span names and hierarchy
# Create custom span
with tracer.start_as_current_span(
    "llm_call") as span:
    span.set_attribute("llm.model", "groq/llama3")
    span.set_attribute("llm.tokens", 1250)
Use both: auto-instrumentation for HTTP/DB plumbing, manual instrumentation for AI-specific logic (LLM calls, agent steps, tool usage).

Instrumenting Python Applications

opentelemetry-python SDK · FastAPI · Custom Spans

Key teaching points: Two approaches — auto-instrumentation (zero-code, covers frameworks like FastAPI, requests, SQLAlchemy) and manual instrumentation (custom spans for business logic like LLM calls and RAG retrieval). Ask the audience: "For AI agents, what operations would you want custom spans around?" Answer: LLM calls (with token counts), retrieval steps, tool invocations, agent reasoning cycles. Demo tip: Show ConsoleSpanExporter first so participants see the raw output before connecting to a backend.

Setting Up the Tracer

# tracing.py — OTel initialization
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.resources import Resource

# 1. Define the service identity
resource = Resource.create({
    "service.name": "agent-api",
    "service.version": "2.0.0",
    "deployment.environment": "production",
})

# 2. Create a TracerProvider with OTLP export
provider = TracerProvider(resource=resource)
processor = BatchSpanProcessor(
    OTLPSpanExporter(endpoint="http://otel-collector:4317")
)
provider.add_span_processor(processor)
trace.set_tracer_provider(provider)

# 3. Get a tracer for your module
tracer = trace.get_tracer("agent.api")
Resource attributes identify which service generated the telemetry. Every span carries these.

Custom Spans for AI Logic

from opentelemetry import trace

tracer = trace.get_tracer("agent.core")

async def process_query(query: str):
    # Parent span for the entire agent workflow
    with tracer.start_as_current_span("agent_workflow") as span:
        span.set_attribute("agent.query", query)

        # Child span: RAG retrieval
        with tracer.start_as_current_span("rag_retrieval") as rag_span:
            docs = await chromadb.query(query, n_results=5)
            rag_span.set_attribute("rag.docs_retrieved", len(docs))
            rag_span.set_attribute("rag.collection", "knowledge_base")

        # Child span: LLM call
        with tracer.start_as_current_span("llm_call") as llm_span:
            response = await llm.invoke(query, context=docs)
            llm_span.set_attribute("llm.model", "groq/llama3-70b")
            llm_span.set_attribute("llm.tokens_in", response.usage.prompt_tokens)
            llm_span.set_attribute("llm.tokens_out", response.usage.completion_tokens)
            llm_span.set_attribute("llm.cost_usd", calculate_cost(response.usage))

        span.set_attribute("agent.tools_used", 2)
        return response.content

Custom Metrics in Python

from opentelemetry import metrics
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.sdk.metrics.export import PeriodicExportingMetricReader
from opentelemetry.exporter.otlp.proto.grpc.metric_exporter import OTLPMetricExporter

# Setup meter provider
reader = PeriodicExportingMetricReader(OTLPMetricExporter())
provider = MeterProvider(metric_readers=[reader])
metrics.set_meter_provider(provider)

meter = metrics.get_meter("agent.api")

# Define metrics
request_counter = meter.create_counter(
    "agent.requests.total",
    description="Total agent requests",
)
token_counter = meter.create_counter(
    "agent.tokens.total",
    description="Total tokens consumed",
)
latency_histogram = meter.create_histogram(
    "agent.request.duration",
    unit="ms",
    description="Request duration in milliseconds",
)

# Record metrics in your handlers
request_counter.add(1, {"endpoint": "/chat", "model": "llama3"})
token_counter.add(1270, {"direction": "total", "model": "llama3"})
latency_histogram.record(342.5, {"endpoint": "/chat"})

Log Correlation with Trace IDs

Configuring OTel in Python

# otel_config.py — Python OTel setup with ConsoleSpanExporter
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import (
    BatchSpanProcessor, ConsoleSpanExporter
)
from opentelemetry.sdk.resources import Resource
import os

# Configure via environment variables or Python
resource = Resource.create({
    "service.name": os.getenv("OTEL_SERVICE_NAME", "agent-api"),
    "service.version": "2.0.0",
    "deployment.environment": "production",
})

provider = TracerProvider(resource=resource)

# ConsoleSpanExporter for local dev (no collector needed)
provider.add_span_processor(
    BatchSpanProcessor(ConsoleSpanExporter())
)
trace.set_tracer_provider(provider)

# Run with: uvicorn app:app --host 0.0.0.0 --port 8000
In production, use sampling (e.g., 10%) to avoid overwhelming your trace backend. Always sample 100% of errors regardless of the ratio.

Question 1 of 5

Which observability pillar is best for answering “Why is this specific request slow?”

A Metrics — check latency percentiles
B Logs — search for slow request entries
C Traces — follow the request path across services
D Alerts — check which alert fired
Answer: Question 1
C — Traces. Traces show the exact path a specific request took through all services, revealing which span (operation) consumed the most time. Metrics show aggregates (p99), not individual requests.
Correct answer: C — Traces. Traces follow a specific request across services, showing which span consumed the most time. Metrics show aggregates (p99 latency), not individual request paths.
Question 2 of 5

What does OTLP stand for and what is its default gRPC port?

A Open Tracing Log Protocol, port 9090
B OpenTelemetry Protocol, port 4317
C OpenTelemetry Protocol, port 4318
D Open Telemetry Log Protocol, port 8080
Answer: Question 2
B — OpenTelemetry Protocol, port 4317. OTLP uses gRPC on port 4317 by default. Port 4318 is for HTTP/protobuf transport. OTLP is the standard wire format for all three signals.
Correct answer: B — OpenTelemetry Protocol, port 4317. OTLP is the standard wire format. gRPC on 4317 is the default; 4318 is for HTTP/protobuf. Common trick question: 4318 is close but wrong for gRPC.
Question 3 of 5

What is the key difference between auto and manual instrumentation?

A Auto is for production, manual is for development only
B Auto creates metrics, manual creates traces
C Auto covers frameworks (HTTP, DB), manual covers business logic (LLM, agent)
D Auto is faster, manual produces more accurate data
Answer: Question 3
C — Auto covers frameworks, manual covers business logic. Auto-instrumentation detects HTTP endpoints, database calls, and external requests. Manual instrumentation is needed for custom spans around LLM calls, RAG retrieval, and agent reasoning steps.
Correct answer: C — Auto covers frameworks (HTTP, DB), manual covers business logic (LLM, agent). Auto-instrumentation detects framework-level operations; manual instrumentation wraps custom business logic like LLM calls and RAG retrieval in spans.
Question 4 of 5

Why should you include trace_id in your log messages?

A It makes logs smaller and more efficient
B It lets you jump from a log entry to its full distributed trace
C It’s required by the OTLP protocol specification
D It prevents duplicate log entries across services
Answer: Question 4
B — Correlate logs with traces. When you find an error in logs, the trace_id lets you click through to the distributed trace in Jaeger/Tempo, showing exactly which service and operation caused the error.
Correct answer: B — It lets you jump from a log entry to its full distributed trace. Including trace_id in logs enables log-to-trace correlation — find an error in logs, click through to the full trace in Jaeger or Tempo.
Question 5 of 5

Which OTel Collector component is responsible for batching, filtering, and transforming telemetry data?

A Receivers
B Processors
C Exporters
D Extensions
Answer: Question 5
B — Processors. The Collector pipeline is: Receivers (accept data) → Processors (batch, filter, transform, sample) → Exporters (send to backends). Processors sit in the middle and modify or filter data in transit.
Correct answer: B — Processors. The OTel Collector pipeline flows: Receivers (accept data) then Processors (batch, filter, transform, sample) then Exporters (send to backends). Processors are the middle stage that modifies data in transit.
