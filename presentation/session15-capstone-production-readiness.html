02

Production Checklist

Everything You Need Before Going Live

Health & Reliability

Health Checks

  • ✓ Readiness probe on /health (HTTP GET)
  • ✓ Liveness probe with appropriate initialDelaySeconds
  • ✓ Startup probe for slow-loading models
  • ✓ Health endpoint checks downstream dependencies

Self-Healing

  • ✓ Deployment (not bare pods)
  • ✓ replicas ≥ 2 for HA
  • ✓ Pod Disruption Budget (minAvailable: 2)
  • ✓ Rolling update strategy (maxUnavailable: 0)
# Production health endpoint (checks dependencies) @app.get("/health") async def health(): checks = { "redis": await redis_client.ping(), "chromadb": await chroma_client.heartbeat(), "model_loaded": agent.is_ready(), } healthy = all(checks.values()) return JSONResponse( status_code=200 if healthy else 503, content={"status": "ok" if healthy else "degraded", "checks": checks} )

Resource Management

Resource Limits

  • ✓ CPU and memory requests set on all containers
  • ✓ CPU and memory limits set (prevent noisy neighbors)
  • ✓ Limits ≥ 2x requests for AI workloads (burst)
  • ✓ Tested under load to validate limits

Autoscaling

  • ✓ HPA configured (CPU target 60–80%)
  • ✓ minReplicas ≥ 2 for high availability
  • ✓ maxReplicas capped (budget protection)
  • ✓ scaleDown stabilization ≥ 300s

Secrets Management

Never Do This

# WRONG: Secrets in code GROQ_API_KEY = "gsk_abc123..." # WRONG: Secrets in ConfigMap kind: ConfigMap data: API_KEY: "gsk_abc123..." # WRONG: Secrets in Dockerfile ENV GROQ_API_KEY=gsk_abc123

Best Practices

# RIGHT: K8s Secret kind: Secret type: Opaque data: GROQ_API_KEY: Z3NrX2FiYzEyMy4uLg== # BETTER: External Secrets Operator # Syncs from AWS Secrets Manager, # HashiCorp Vault, Azure Key Vault
  • ✓ API keys in K8s Secrets (not ConfigMaps or code)
  • ✓ Secrets injected via envFrom: secretRef
  • ✓ .gitignore prevents committing secrets
  • ✓ RBAC limits who can read secrets
  • ✓ Rotate secrets regularly (External Secrets Operator helps)

Logging & Monitoring

Logging Checklist

  • ✓ Structured JSON logging (not print statements)
  • ✓ trace_id injected via OTel LoggingInstrumentor
  • ✓ Log levels: DEBUG (dev), INFO (prod), ERROR (always)
  • ✓ No sensitive data in logs (PII, API keys)
  • ✓ Stdout/stderr (K8s collects container logs)

Monitoring Checklist

  • ✓ /metrics endpoint with Prometheus counters, histograms
  • ✓ Pod annotations for auto-discovery
  • ✓ Grafana dashboard with RED metrics
  • ✓ AI-specific metrics (tokens, cost, latency per model)
  • ✓ LangFuse for LLM trace analysis

Alerting Configuration

Alert Condition Severity Action
Agent Down up{job="agent-api"} == 0 for 1m critical PagerDuty on-call
High Error Rate 5xx rate > 5% for 5m critical Slack #incidents
High Latency p99 > 10s for 10m warning Slack #monitoring
Cost Spike Token cost > 2x daily avg for 30m warning Slack #costs
ChromaDB Storage PVC usage > 80% warning Slack #infrastructure
Pod OOMKilled OOM events > 0 in 5m critical PagerDuty + Slack
Start with critical alerts (down, high error rate, OOM) and add warning alerts (latency, cost, storage) as you learn your baseline.

Backup & Recovery

What to Back Up

  • ✓ ChromaDB PVC (vector embeddings)
  • ✓ LangFuse PostgreSQL (traces, prompts, scores)
  • ✓ Kubernetes manifests (GitOps = infrastructure as code)
  • ✓ Prometheus data (optional, metrics are rebuildable)
  • ✓ Grafana dashboards (export as JSON)

Recovery Strategy

  • ✓ PVC snapshots (VolumeSnapshot API)
  • ✓ PostgreSQL pg_dump on schedule
  • ✓ GitOps: all manifests in version control
  • ✓ Tested disaster recovery runbook
  • ✓ RTO/RPO defined for each component
Vector embeddings in ChromaDB are expensive to regenerate (re-process all documents). Back up the PVC regularly. Redis cache is ephemeral and can be rebuilt.

Building production AI systems requires: orchestration (LangChain), state management (LangGraph), retrieval (RAG), and tool integration — not just picking a model.

AI systems are non-deterministic. You must trace LLM calls, track costs, and monitor agent behavior. Flying blind leads to runaway costs and hallucinations.

4. Production is a Mindset

Health probes, resource limits, secrets management, autoscaling, alerts, backups — these aren’t extras, they’re the difference between a demo and a product.

Question 1 of 5

What is the correct deployment order for the capstone AI stack?

A Agent first, then data layer, then observability
B Config → Data layer → Observability → Application → Ingress
C Observability first so you can monitor everything being deployed
D Order doesn’t matter with Kubernetes — it resolves dependencies automatically
B — Dependencies first. Config/Secrets must exist before pods reference them. Data layer (Redis, ChromaDB) must be running before the agent connects. Observability should be ready to capture the agent’s first requests. Ingress comes last.
Question 2 of 5

Why should your /health endpoint check downstream dependencies (Redis, ChromaDB)?

A To make the health check slower and more thorough
B Kubernetes requires dependency checks in readiness probes
C So the readiness probe fails when dependencies are down, stopping traffic to a pod that can’t serve requests
D To restart the pod automatically when dependencies fail
C — Stop routing traffic to broken pods. If Redis or ChromaDB is down, the agent can’t serve requests properly. By failing the readiness probe, Kubernetes removes the pod from the Service endpoints, preventing users from hitting a broken pod.
Question 3 of 5

Where should API keys (like GROQ_API_KEY) be stored in a Kubernetes deployment?

A In the Dockerfile as ENV variables
B In a ConfigMap for easy access
C In a Kubernetes Secret, injected via envFrom: secretRef
D Hardcoded in the Python application code
C — Kubernetes Secrets. Secrets are base64-encoded and can be access-controlled via RBAC. They’re injected as environment variables at runtime. For even better security, use External Secrets Operator to sync from AWS Secrets Manager or HashiCorp Vault.
Question 4 of 5

Which component from the capstone should NOT be treated as ephemeral (must be backed up)?

A Redis cache data
B ChromaDB vector embeddings (PVC data)
C Agent API container filesystem
D Prometheus metrics (last 15 days)
B — ChromaDB embeddings. Vector embeddings are expensive to regenerate (requires re-processing all documents). Redis cache rebuilds automatically. Prometheus metrics can be re-collected. ChromaDB PVC should be backed up via VolumeSnapshots.
Question 5 of 5

What is the most important lesson from this 5-day course?

A The latest and largest LLM model is always the best choice
B Kubernetes is too complex for AI applications
C Production AI requires the full stack: orchestration, containers, K8s, observability, and operational practices
D Observability should be added only after an incident occurs
C — Full stack matters. A great AI model in a bad deployment is worse than a good model in a great deployment. Production AI needs: LangChain/LangGraph (orchestration), MCP (dev tools), FastAPI (serving), and Prometheus/LangFuse (observability).
