FastAPI for AI Agents

REST API Patterns · Agent Endpoints · Async Design

Ask the audience: how many of you have used Flask or Django for APIs? FastAPI is purpose-built for async workloads like LLM inference. The key insight here is that LLM calls are I/O-bound, not CPU-bound, so async is a natural fit. Stress that Pydantic integration means you get free validation and docs.

Why FastAPI for AI Applications?

Async-Native

Built on ASGI — handles concurrent LLM calls without blocking threads

Pydantic Integration

Automatic request/response validation with type hints

Auto-Generated Docs

Swagger UI at /docs — instant API documentation for your team

Lightweight

Low memory footprint — ideal for resource-constrained environments

FastAPI is like a well-organized kitchen. The prep area (Pydantic) validates ingredients before they reach the chef (your agent). The serving window (async responses) keeps orders flowing even when one dish takes longer.

Basic Agent Endpoint

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(title="AI Agent API")

class AgentRequest(BaseModel):
    query: str
    session_id: str | None = None
    max_tokens: int = 1024

class AgentResponse(BaseModel):
    answer: str
    sources: list[str] = []
    tokens_used: int
    latency_ms: float

@app.post("/agent/invoke", response_model=AgentResponse)
async def invoke_agent(request: AgentRequest):
    # Agent logic here
    result = await agent.ainvoke(request.query)
    return AgentResponse(
        answer=result["output"],
        sources=result.get("sources", []),
        tokens_used=result["token_count"],
        latency_ms=result["latency"]
    )
02

Pydantic Models

Request/Response Validation · Type Safety · Serialization

This section is about trusting nothing at the boundary. Ask: what happens if a client sends temperature=5.0 or max_tokens=-1? Without Pydantic, those bad values flow straight into your LLM call and waste money or cause errors. Emphasize the field_validator pattern for custom business rules.

Pydantic for AI Applications

Validate everything at the boundary

from pydantic import BaseModel, Field, field_validator

class ChatMessage(BaseModel):
    role: str = Field(..., pattern="^(user|assistant|system)$")
    content: str = Field(..., min_length=1, max_length=10000)

class AgentRequest(BaseModel):
    messages: list[ChatMessage]
    model: str = "llama-3.3-70b-versatile"
    temperature: float = Field(0.7, ge=0.0, le=2.0)
    max_tokens: int = Field(1024, ge=1, le=8192)

    @field_validator("messages")
    def must_have_user_message(cls, v):
        if not any(m.role == "user" for m in v):
            raise ValueError("Must include at least one user message")
        return v
Pydantic catches malformed requests before they reach your agent. Invalid temperature? Missing messages? Rejected instantly with a clear error.
03

Streaming Responses

Server-Sent Events · Real-Time Output · User Experience

Ask: how long will users wait before abandoning a request? Research says about 3-5 seconds. LLM calls often take 10-30 seconds. Streaming solves this by showing the first token in about 200ms. Mention that ChatGPT, Claude, and every production AI product uses streaming for exactly this reason.

SSE for Real-Time Agent Output

Don't make users stare at a spinner for 30 seconds

from fastapi.responses import StreamingResponse
import json

@app.post("/agent/stream")
async def stream_agent(request: AgentRequest):
    async def event_generator():
        async for chunk in agent.astream(request.query):
            data = json.dumps({"token": chunk})
            yield f"data: {data}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream"
    )

Why stream?

  • First token in ~200ms instead of waiting 5-30s
  • Users can read as output is generated
  • Can cancel mid-stream if wrong direction

Client-side (JavaScript)

  • Use EventSource or fetch with reader
  • Append each token to UI progressively
  • Handle [DONE] to finalize output

Health Checks & Monitoring

Health Endpoints · Process Monitoring · Startup Delays

This is critical for production deployments. Ask: what happens if your AI app takes 2 minutes to load the model but monitoring expects a healthy response in 30 seconds? Monitoring systems might incorrectly report failures. Stress the three-endpoint model: startup health (give me time to load), liveness health (am I stuck?), readiness health (am I ready for traffic?).

The /health Endpoint Pattern

@app.get("/health")
async def health_check():
    return {
        "status": "healthy",
        "version": "1.2.0",
        "checks": {
            "llm_provider": await check_groq_connection(),
            "vector_db": await check_chromadb(),
            "memory_mb": get_memory_usage(),
        }
    }

@app.get("/ready")
async def readiness_check():
    # Only return 200 when the app can serve traffic
    if not model_loaded:
        raise HTTPException(status_code=503, detail="Model not loaded")
    return {"status": "ready"}

/health (Liveness)

Is the process alive?
"Monitor for crashes."

/ready (Readiness)

Can I serve traffic?
"Model still loading."

Startup Delay

Initial load time?
"Give me time to warm up."

Python Health Monitoring

# health_monitor.py — async HealthChecker class
import asyncio, signal, httpx, psutil

class HealthChecker:
    """Monitors /health endpoint and manages process lifecycle."""

    def __init__(self, url="http://localhost:8000/health",
                 interval=30, timeout=5, retries=3, start_delay=120):
        self.url = url
        self.interval = interval
        self.timeout = timeout
        self.retries = retries
        self.start_delay = start_delay
        self.failures = 0

    async def check(self):
        try:
            async with httpx.AsyncClient() as client:
                resp = await client.get(self.url, timeout=self.timeout)
                if resp.status_code == 200:
                    self.failures = 0
                    return True
        except Exception:
            pass
        self.failures += 1
        return self.failures < self.retries

    async def run(self):
        await asyncio.sleep(self.start_delay)
        while True:
            if not await self.check():
                logger.error("Health check failed, shutting down")
                break
            await asyncio.sleep(self.interval)

# Graceful shutdown via signal handlers
signal.signal(signal.SIGTERM, lambda s, f: asyncio.get_event_loop().stop())
AI apps can take minutes to load models. Use start_delay to give the application time to initialize before health checks begin counting failures.

Secrets Management

.env Files · python-dotenv · Environment Variables

Ask the audience: has anyone ever accidentally committed an API key to git? This happens constantly, and with LLM API keys costing real money, leaked keys can run up large bills. The key takeaway is: .env.example goes in the repo with placeholder values, .env with real values stays in .gitignore.

Configuration vs Secrets

Aspect .env File (config) .env File (secrets)
Purpose Non-sensitive configuration Sensitive credentials
Storage Checked into repo (.env.example) Never checked in (.gitignore)
Examples Model name, temperature, max_tokens GROQ_API_KEY, DB passwords
Access Readable by team Restricted, per-environment
Python dotenv load_dotenv(".env") load_dotenv(".env.secrets") 

# .env.example (committed to repo — no real values)
GROQ_API_KEY=your-groq-api-key-here
LANGFUSE_SECRET_KEY=your-langfuse-secret-here
LANGFUSE_PUBLIC_KEY=your-langfuse-public-here

# .env (local only — in .gitignore)
GROQ_API_KEY=gsk_abc123...
LANGFUSE_SECRET_KEY=sk-lf-xyz...

# Python — inject via python-dotenv
from dotenv import load_dotenv
load_dotenv(".env")     # loads into os.environ
import os
api_key = os.getenv("GROQ_API_KEY")
Never hardcode API keys in source code. Use .env files with .gitignore and python-dotenv for environment variable injection. Rotate keys regularly.

Structured Logging

JSON Logs · AI-Specific Fields · Correlation

This connects directly to Session 10 and 11 on observability. Ask: how do you find out why a particular request was slow last Tuesday at 3am? With print statements, you cannot. With structured JSON logs including trace_id, model name, token counts, and cost, you can filter and aggregate instantly. Stress the AI-specific fields that traditional logging misses.

JSON Logs vs print()

Bad: print()

print("Agent called with query: " + query)
print("Tokens used: 247")
print("Error: rate limit exceeded")
  • No structure — hard to parse
  • No timestamps
  • Cannot filter or aggregate

Good: Structured JSON

{"timestamp": "2026-02-12T10:30:00Z",
 "level": "INFO",
 "trace_id": "abc-123",
 "model": "llama-3.3-70b-versatile",
 "tokens_in": 142,
 "tokens_out": 247,
 "cost_usd": 0.0003,
 "latency_ms": 1840,
 "message": "Agent invocation complete"}
  • Machine-parseable
  • Searchable in LangFuse/ELK
  • Correlate with traces

AI-Specific Log Fields

What to include beyond standard application logs

Field Purpose Example Value
trace_id Correlate logs across request lifecycle abc-123-def
model Which LLM was used llama-3.3-70b-versatile
tokens_in / tokens_out Token usage for cost tracking 142 / 247
cost_usd Estimated cost per invocation 0.0003
tools_called Which tools were invoked ["search", "calculator"]
agent_steps Number of think-act-observe loops 3
These fields let you answer critical production questions: How much is this costing? Which models are slow? Are tools failing silently?

Deployment Order

Correct Sequencing for Reliable Rollouts

Ask: what happens if you start the app before the database is running? The app crashes on first connection attempt, health checks fail, and monitoring systems report errors. The kitchen analogy works well here -- you do not invite guests before the stove is installed. Walk through each step and ask what breaks if you skip it.

Deploy in the Right Order

Dependencies must exist before dependents

Step 1: .env Files & Configuration Configuration
↓
Step 2: Databases & Vector Stores (local storage) Data Layer
↓
Step 3: LangFuse + Observability Stack Observability
↓
Step 4: AI Agent Application (uvicorn process) Application
↓
Step 5: Port Mapping / Reverse Proxy Routing
You wouldn't invite dinner guests before the kitchen is built, the stove is installed, and the ingredients are stocked. Deploy infrastructure first, then the application.

Resource Monitoring

Monitor memory and process health

Component Typical Memory Monitor With Alert Threshold
AI Agent (FastAPI) 512 MB - 1 GB psutil, /health endpoint > 1.5 GB
ChromaDB 512 MB - 1 GB Process monitoring > 1.5 GB
LangFuse + PostgreSQL 256 MB - 512 MB Process monitoring > 768 MB
Total System ~2-3 GB System monitoring (htop, top) > 6 GB (on 8 GB system)
On the 8 GB GitHub Codespaces free tier, monitor total memory usage. Use psutil in Python to track process memory and restart if thresholds are exceeded. In production, use process managers like systemd or supervisord.

Error Handling Patterns

HTTPException · Status Codes · Fallbacks

This is where most AI applications fall short. Ask: what does your app return when Groq rate-limits you? If it returns a generic 500, the client has no idea whether to retry or give up. Stress the importance of specific HTTP status codes -- 429 means retry after delay, 504 means the LLM timed out, 503 means the service is not ready.

Robust Error Handling

from fastapi import HTTPException
import logging

logger = logging.getLogger("ai_agent")

@app.post("/agent/invoke")
async def invoke_agent(request: AgentRequest):
    try:
        result = await agent.ainvoke(request.query)
        return AgentResponse(answer=result["output"])

    except RateLimitError:
        logger.warning("Rate limit hit", extra={"model": request.model})
        raise HTTPException(
            status_code=429,
            detail="LLM rate limit exceeded. Retry after 60s."
        )
    except ModelTimeoutError:
        logger.error("Model timeout", extra={"latency_ms": elapsed})
        raise HTTPException(
            status_code=504,
            detail="LLM inference timed out."
        )
    except Exception as e:
        logger.exception("Unhandled error")
        raise HTTPException(
            status_code=500,
            detail="Internal server error."
        )

HTTP Status Codes for AI APIs

Code Meaning AI Use Case
200 Success Agent completed successfully
400 Bad Request Invalid prompt, missing required fields
422 Unprocessable Entity Pydantic validation failed
429 Too Many Requests LLM provider rate limit exceeded
500 Internal Server Error Unhandled exception in agent logic
503 Service Unavailable Model not loaded, dependency down
504 Gateway Timeout LLM inference took too long
Use specific status codes so clients can implement appropriate retry logic. A 429 means "wait and retry." A 500 means "something is broken."

Testing AI Applications

Unit Tests · Mocking LLMs · Integration Tests

Ask: how many of you write tests for your AI code today? Testing AI is different from testing traditional software because LLM outputs are non-deterministic. The key insight is to test everything around the LLM deterministically -- Pydantic validation, error handling, tool routing -- and mock the LLM itself for repeatable assertions.

Testing Strategies for AI

Unit Tests

  • Test Pydantic model validation
  • Test utility functions (token counting, cost calculation)
  • Test error handling paths
  • Fast, deterministic, no LLM calls

Mock LLM Tests

  • Replace LLM with fixed responses
  • Test agent routing and tool selection
  • Test streaming behavior
  • Fast, no API costs

Integration Tests

  • End-to-end with real (or staging) LLM
  • Test full request → response flow
  • Test database interactions
  • Slow, but catches real issues

Evaluation Tests

  • Measure answer quality over a test set
  • Track accuracy, relevance, faithfulness
  • Catch model regressions on upgrade
  • LLM-as-judge or human review

Mocking LLMs in Tests

from unittest.mock import AsyncMock, patch
from httpx import AsyncClient
import pytest

@pytest.mark.asyncio
async def test_agent_invoke():
    # Mock the LLM to return a fixed response
    mock_response = {"output": "Paris is the capital of France."}

    with patch("app.agent.ainvoke", new_callable=AsyncMock) as mock:
        mock.return_value = mock_response

        async with AsyncClient(app=app, base_url="http://test") as client:
            resp = await client.post("/agent/invoke", json={
                "query": "What is the capital of France?"
            })

        assert resp.status_code == 200
        assert "Paris" in resp.json()["answer"]
        mock.assert_called_once()
Mock the LLM at the boundary. Test everything around it deterministically. Save real LLM calls for integration and evaluation tests.

Session 11 Quiz

5 questions · Production Development & Deployment

Question 1 of 5

Why is FastAPI a good fit for serving AI agents?

A It has a built-in LLM inference engine
B It is async-native, handles concurrent LLM calls without blocking, and integrates Pydantic for validation
C It is the only Python framework that supports streaming
D It automatically scales to multiple servers
Answer: Question 1
B — Async + Pydantic. FastAPI’s ASGI foundation handles concurrent LLM calls efficiently, and Pydantic integration validates requests before they reach your agent logic.
Correct answer is B. FastAPI does not include its own LLM engine, nor is it the only framework supporting streaming. The critical advantage is async-native I/O for concurrent LLM calls plus built-in Pydantic validation for request and response schemas.
Question 2 of 5

What is the difference between a liveness probe and a readiness probe?

A Liveness checks if the model is loaded; readiness checks if the process is running
B They are the same thing with different names
C Liveness checks if the process is alive (restart if stuck); readiness checks if it can serve traffic (don’t route requests yet)
D Liveness runs once at startup; readiness runs continuously
Answer: Question 2
C — Alive vs. ready. Liveness answers “should I restart this process?” Readiness answers “should I send traffic here?” A process can be alive but not ready (e.g., still loading a model).
Correct answer is C. A common confusion is thinking they are the same. The classic example: your app process is running (liveness passes) but the model file is still downloading (readiness fails). Monitoring systems should not send traffic until readiness passes, but should not restart the process because liveness is fine.
Question 3 of 5

Why should API keys never be hardcoded in source code?

A Hardcoded keys make the application run slower
B Python cannot read hardcoded strings at runtime
C They get committed to version control and exposed; use .env files with .gitignore and python-dotenv instead
D Hardcoded keys cannot be rotated without recompiling
Answer: Question 3
C — Security risk. Hardcoded keys in source code end up in git history and are nearly impossible to fully remove. Use .env files (in .gitignore) and load them via python-dotenv.
Correct answer is C. Even if you delete a hardcoded key in a later commit, it remains in git history forever unless you rewrite history. The .env plus .gitignore pattern is the minimum viable approach. In production, use a secrets manager like AWS Secrets Manager or HashiCorp Vault.
Question 4 of 5

What advantage does structured JSON logging have over print() statements?

A JSON logs are smaller in file size than print output
B JSON logs are machine-parseable, searchable, filterable, and can include trace_id, token counts, and cost fields
C print() statements are not captured by any logging system
D JSON logs automatically fix application errors
Answer: Question 4
B — Machine-parseable with AI-specific fields. Structured logs let you search, filter, and aggregate in tools like LangFuse or ELK. Adding trace_id, model, tokens_in/out, and cost_usd fields answers critical production questions.
Correct answer is B. Print statements are actually captured by some logging systems, but they lack structure. The real advantage of JSON logging is that you can filter by trace_id, aggregate token costs across requests, and set up alerts on specific fields -- none of which is possible with unstructured print output.
Question 5 of 5

What is the correct deployment order for an AI application stack?

A Application → Database → Config → Observability → Routing
B Routing → Application → Config → Database → Observability
C Config/Secrets → Databases → Observability → Application → Routing
D The order does not matter as long as everything is deployed
Answer: Question 5
C — Dependencies first. Config and secrets must exist before anything reads them. Databases must be running before the app connects. Observability should be ready to capture the app’s first logs. Only then do you expose the app via routing.
Correct answer is C. Order matters because each layer depends on the one below it. If you expose routing before the application is ready, users get errors. If you start the application before the database is up, the app crashes on first query. Always deploy bottom-up: infrastructure, then services, then routing.
