StateGraph Fundamentals

What is LangGraph · Why Graphs · Defining State

Why LangGraph?

When agents aren't enough

ReAct Agent (Session 5)

  • LLM decides everything at runtime
  • Great for flexible, open-ended tasks
  • Hard to guarantee specific steps run
  • Difficult to add human approval
  • Limited control over execution flow

LangGraph (Today)

  • YOU define the workflow structure
  • Explicit nodes, edges, and conditions
  • Guaranteed execution order where needed
  • Built-in human-in-the-loop support
  • Full state management and persistence
A ReAct agent is like a freelancer who decides their own process. LangGraph is like a project manager's Kanban board — clear stages, defined transitions, approval gates, and every task's status is tracked.

What is a StateGraph?

A workflow defined as nodes + edges + state

START
→
Classify
Node
→
Route?
→
Handle A
Handle B
→
END

State

A shared data dictionary that flows through the graph. Each node reads and updates it.

Nodes

Python functions that process the state. Each node does one step of work.

Edges

Connections between nodes. Can be fixed or conditional (branching).

Defining State with TypedDict

The shared data structure for your workflow

from typing import TypedDict, Annotated
from operator import add
from langgraph.graph import StateGraph

# Define the state schema
class WorkflowState(TypedDict):
    messages: Annotated[list, add]  # append new items to list
    current_step: str             # overwrite on update
    approved: bool                # overwrite on update

# Create the graph with this state
graph = StateGraph(WorkflowState)

Regular Fields

Fields like str, bool, int get overwritten when a node returns a new value. Last write wins.

Annotated Fields (Reducers)

Annotated[list, add] means new values are appended to the list, not replaced. This is perfect for message history.

Your First LangGraph Workflow

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    name: str
    greeting: str

# Node: a function that takes state and returns updates
def greet(state: State) -> dict:
    return {"greeting": f"Hello, {state['name']}! Welcome to UniGPS."}

# Build the graph
graph = StateGraph(State)
graph.add_node("greet", greet)
graph.add_edge(START, "greet")  # START → greet
graph.add_edge("greet", END)     # greet → END

# Compile and run
app = graph.compile()
result = app.invoke({"name": "Priya"})
print(result["greeting"])  # "Hello, Priya! Welcome to UniGPS."
Every graph follows three steps: define state (TypedDict), add nodes (Python functions), connect with edges (START → nodes → END). Then compile() and invoke().

When to Use What?

Feature ReAct Agent LangGraph Workflow
Control flow LLM decides everything You define the structure
Best for Open-ended Q&A, exploration Structured processes, pipelines
Human approval Not built-in Built-in interrupt/resume
Error handling LLM retries or gives up Explicit retry nodes & fallbacks
State management Message list only Full typed state with reducers
Complexity Simple to set up More code but more predictable
Rule of thumb: If the LLM needs to figure out what to do → use an agent. If you know the steps but need the LLM at certain stages → use LangGraph. You can even combine both — put agents inside graph nodes!

Nodes & Edges

Processing Steps · Connections · Conditional Routing

Nodes: Processing Steps

Each node is a Python function that transforms state

# A node receives the full state and returns updates
def classify_request(state):
    """Classify whether a request is HR, Tech, or Finance."""
    message = state["message"]
    if "leave" in message.lower() or "wfh" in message.lower():
        return {"category": "hr"}
    elif "deploy" in message.lower() or "database" in message.lower():
        return {"category": "tech"}
    return {"category": "general"}

graph.add_node("classify", classify_request)

Node Rules

  • Takes the full state as input
  • Returns a dict with state updates
  • Only returned keys are updated
  • Non-returned keys stay unchanged

Node Types

  • Pure logic: classify, validate, transform
  • LLM-powered: call an LLM inside the node
  • Tool-calling: run tools or APIs
  • Side effects: send emails, write to DB

Edges: Connections Between Nodes

Normal Edge

Always go from A to B.

graph.add_edge(
  "classify",
  "respond"
)

Entry Edge

Where the graph starts.

graph.add_edge(
  START,
  "classify"
)

Exit Edge

Where the graph ends.

graph.add_edge(
  "respond",
  END
)
START
→
classify
→
respond
→
END

Conditional Edges

Route to different nodes based on state

# Routing function — reads state and returns next node name
def route_request(state) -> str:
    if state["category"] == "hr":
        return "handle_hr"
    elif state["category"] == "tech":
        return "handle_tech"
    return "handle_general"

# Add conditional edge from "classify" node
graph.add_conditional_edges(
    "classify",              # source node
    route_request,          # routing function
    {                        # mapping: return value → node name
        "handle_hr": "handle_hr",
        "handle_tech": "handle_tech",
        "handle_general": "handle_general",
    }
)
Conditional edges let you build branching workflows. The routing function reads the current state and returns the name of the next node to execute. This is how you create if/else logic in your graph.

Complete Branching Workflow

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    message: str
    category: str
    response: str

def classify(state): return {"category": "hr" if "leave" in state["message"] else "tech"}
def handle_hr(state): return {"response": "HR: You get 24 annual leave days."}
def handle_tech(state): return {"response": "Tech: Use FastAPI for new services."}
def route(state): return "hr_node" if state["category"] == "hr" else "tech_node"

graph = StateGraph(State)
graph.add_node("classify", classify)
graph.add_node("hr_node", handle_hr)
graph.add_node("tech_node", handle_tech)

graph.add_edge(START, "classify")
graph.add_conditional_edges("classify", route, {"hr_node": "hr_node", "tech_node": "tech_node"})
graph.add_edge("hr_node", END)
graph.add_edge("tech_node", END)

app = graph.compile()
result = app.invoke({"message": "How many leave days?"})
print(result["response"])  # "HR: You get 24 annual leave days."

Cycles: Looping Back

Edges can create loops for retry or refinement

START
→
Draft
→
Review
→
Good?
→
END

If review fails → loop back to Draft (cycle!)

def should_continue(state) -> str:
    if state["quality_score"] >= 8:
        return "end"      # Good enough, finish
    if state["attempts"] >= 3:
        return "end"      # Too many retries, stop
    return "retry"        # Loop back to draft

graph.add_conditional_edges("review", should_continue, {
    "end": END,
    "retry": "draft",  # ← loop back!
})
Unlike simple chains, LangGraph supports cycles — edges that go backward. This is powerful for retry logic, iterative refinement, and self-correcting workflows. Always include a max-retry guard to prevent infinite loops.

Checkpointing & Human-in-the-Loop

State Persistence · Interrupt · Resume · Approval Gates

Checkpointing: Save & Resume State

Persist workflow state at every step

from langgraph.checkpoint.memory import MemorySaver

# Compile with a checkpointer
memory = MemorySaver()
app = graph.compile(checkpointer=memory)

# Run with a thread_id — state is saved after each node
config = {"configurable": {"thread_id": "workflow-001"}}
result = app.invoke({"message": "How many leave days?"}, config)

# Later: inspect the saved state
snapshot = app.get_state(config)
print(snapshot.values)      # Full state at last checkpoint
print(snapshot.next)        # Which node runs next (or empty if done)

Development

MemorySaver() — in-memory, fast, lost on restart. Perfect for dev/testing.

Production

SqliteSaver(db_path) or PostgresSaver(conn) — persistent, survives restarts, scales.

Inspecting Workflow State

# Get the current state snapshot
snapshot = app.get_state(config)

# What data is in the state?
print(snapshot.values)
# {"message": "How many leave days?", "category": "hr", "response": "24 days"}

# Which node runs next? (empty tuple = workflow is done)
print(snapshot.next)
# () ← empty means workflow completed

# You can even UPDATE the state manually
app.update_state(config, {"approved": True})
# Then resume: app.invoke(None, config)
Checkpointing gives you full visibility into your workflow. You can inspect the state at any point, see which node runs next, and even manually update the state before resuming — this is the foundation for human-in-the-loop.

Human-in-the-Loop

Pause the workflow for human approval

Draft
email
→
PAUSE
Human reviews
→
Send
email
→
END
# Compile with interrupt_before — pauses BEFORE "send_email" runs
app = graph.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["send_email"]  # ← pause point
)

# Run — stops before send_email
result = app.invoke({"request": "Draft an email to the team"}, config)
# Workflow paused! Human reviews the draft...

# Human approves → resume from where it paused
result = app.invoke(None, config)  # ← None means "continue"
# send_email node now executes

Human Edits Before Resuming

The human can modify the state before approving

# Step 1: Run until pause point
result = app.invoke({"request": "Draft email to team about Friday lunch"}, config)

# Step 2: Inspect what the draft node produced
snapshot = app.get_state(config)
print(snapshot.values["draft"])
# "Hi team, lunch on Friday at 1 PM."

# Step 3: Human edits the draft
app.update_state(config, {
    "draft": "Hi team, Friday lunch at 12:30 PM at the cafeteria. See you there!"
})

# Step 4: Resume — sends the edited version
result = app.invoke(None, config)
Human-in-the-loop isn't just approve/reject. The human can inspect the state, modify values, and resume. This is critical for production AI: draft emails, review generated content, approve financial transactions, validate data.

Interrupt Strategies

interrupt_before

Pause before a node runs. Use when the human should review the state before an action happens.

# Pause before sending
interrupt_before=["send_email"]

Common: send emails, make payments, delete data

interrupt_after

Pause after a node runs. Use when the human should review the output of a step.

# Pause after drafting
interrupt_after=["draft_email"]

Common: review drafts, verify classifications, check data

Checkpoint Backends

Backend Import Persistence Use Case
MemorySaver langgraph.checkpoint.memory In-memory (lost on restart) Development, testing, demos
SqliteSaver langgraph.checkpoint.sqlite Local file (survives restart) Single-server production
PostgresSaver langgraph.checkpoint.postgres Remote database (scalable) Multi-server production
# Switch from dev to production — just change the checkpointer!
# memory = MemorySaver() ← development
memory = SqliteSaver.from_conn_string("checkpoints.db")  # ← production
app = graph.compile(checkpointer=memory)

Answer: Question 2
What does Annotated[list, add] do in a LangGraph state definition?
A It makes the list read-only
B It appends new values to the list instead of replacing it
C It limits the list to a maximum size
D It sorts the list automatically
Why B? Annotated[list, add] defines a reducer. When a node returns a list for this field, the values are appended (using operator.add) rather than overwriting. This is how message histories accumulate across nodes. Without the annotation, returning a new list would replace the old one.

Answer: Question 3
How do you create a branching workflow where different inputs go to different nodes?
A Use add_conditional_edges() with a routing function
B Use add_edge() with multiple destinations
C Put if/else inside the compile() call
D Create separate graphs for each branch
Why A? add_conditional_edges(source, routing_fn, mapping) takes a routing function that reads the current state and returns the name of the next node. The mapping dict maps return values to node names. add_edge() only supports a single fixed destination.

Answer: Question 4
What does interrupt_before=["send_email"] do in a compiled graph?
A It deletes the "send_email" node from the graph
B It pauses the workflow before the node runs, waiting for human approval to continue
C It runs the "send_email" node in a separate thread
D It skips the "send_email" node entirely
Why B? interrupt_before creates a pause point. The workflow runs normally until it reaches "send_email", then stops. A human can inspect the state, optionally modify it, and call invoke(None, config) to resume. The node is not skipped or deleted.

Answer: Question 5
How do you resume a workflow that was paused by an interrupt?
A Call app.restart(config)
B Call app.invoke(None, config) with the same config/thread_id
C Create a new graph and call invoke() with the original state
D Call app.compile(resume=True)
Why B? Passing None as the input tells LangGraph "continue from where you left off." The checkpointer saved the state at the interrupt point. Using the same thread_id in config lets it find the paused workflow. You can also call update_state() before resuming to modify the state.
